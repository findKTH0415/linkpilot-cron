## 1부. 실사 — **고치기 전에 재 본 것** 〈2026-09-14 · 두 저장소 실측〉

지침 §20 의 1·2번이 **읽기 전용 실사**를 첫 칸으로 못박는다. 그래서 먼저 셌다.

### 1.1 ★★★ 결론 — **이 일은 「연결」이 아니라 「식별자를 새로 놓는 일」이다**

지침 §11.1 이 요구하는 **필수 식별자 열일곱** 중 **핵심 일곱이 두 저장소에 0회**다.

| 식별자 | 실측 | 상태 |
|---|---:|---|
| `contact_id` | **0회** | `NOT_IMPLEMENTED` |
| `company_id` | **0회** | `NOT_IMPLEMENTED` |
| `device_contact_id` | **0회** | `NOT_IMPLEMENTED` |
| `business_card_id` | **0회** | `NOT_IMPLEMENTED` |
| `call_id` | **0회** | `NOT_IMPLEMENTED` |
| `link_status` | **0회** | `NOT_IMPLEMENTED` |
| `approval_status` | **0회** | `NOT_IMPLEMENTED` |

★ **그런데 명함·OCR 자체는 이미 있다** — 「명함」 159회 · 「OCR」 93회 · `cardImage` 140회 ·
  `lp_cimg`(명함 이미지 보관) 55회 · `confidence` 13회 · `prevCards`(이전 명함 이력) 6회.

★★ **그러므로 이 일은 둘로 갈린다.**
  · **찍고 읽는 것**은 이미 돈다 → 고치는 일
  · **한 사람을 가리키는 번호를 놓고 그것으로 잇는 것**은 **아예 없다** → 새로 만드는 일
  이렇게 안 적으면 「연동만 하면 된다」로 읽혀 **일정이 몇 배 틀린다.**

### 1.2 기능별 상태 — 지침이 정한 다섯 낱말로

| # | 지침이 요구하는 것 | 실측 | 상태 |
|---|---|---|---|
| 1 | 명함 촬영·이미지 등록 | `cardImage` 140회 · 보관키 `lp_cimg` 55회 | `IMPLEMENTED` |
| 2 | OCR 필드 추출 | 「OCR」 93회 · `confidence` 13회 | `IMPLEMENTED` |
| 3 | OCR 신뢰도 처리 | 「신뢰도」 8회 — **낮을 때의 갈래는 못 쟀다** | `PARTIAL` |
| 4 | 전화번호 **국제형식 정규화** | `normalizePhone` 0회 · `E.164` 0회 · `+82` 5회 | `NOT_IMPLEMENTED` |
| 5 | LinkPilot 안에서 중복검색 | 「중복」 53회 중 **명함 근처 9회** · 「병합」 51 중 11 | `PARTIAL` |
| 6 | **휴대전화 연락처** 검색·저장 | `navigator.contacts` **0회** · `ContactsManager` **0회** · vCard **0회** | `NOT_IMPLEMENTED` |
| 7 | 연락처 **권한 요청** | 위와 같음 — 요청할 API 가 안 붙어 있다 | `NOT_IMPLEMENTED` |
| 8 | 비교·확인 화면 | 「후보」 34회 — **명함 갈래인지는 못 쟀다** | `UNVERIFIED` |
| 9 | 통화·일정·할일·프로젝트·딜을 `contact_id` 로 연결 | 식별자가 0회 | `NOT_IMPLEMENTED` |
| 10 | 변경이력 | `prevCards` 6회 (이전 회사·직함 보관) | `PARTIAL` |
| 11 | Android·iPhone 실기기 검증 | **이 자리에서 못 잰다** | `UNVERIFIED` |
| 12 | Validation Manager 독립 검증 | 실체 없음 — **D-202 로 이미 미결** | `NOT_IMPLEMENTED` |

### 1.3 ★★★ 재는 법이 틀렸던 자리 — **하나 잡았다**

처음 셀 때 **vCard 가 10회**로 나왔다. 그런데 그 열 번은 전부 `srvCardRef` **안의 글자**였다 —
「s-r-**v-C-a-r-d**-Ref」. **낱말 경계 없이 센 것**이다.

★ 낱말 경계로 다시 세니 **0회**다. 「연락처를 기기에 내보내는 길이 있다」로 적을 뻔했고,
  그러면 **없는 기능을 있다고 보고**하는 것이 된다.

★★ **잣대는 하나다 — 「그 숫자를 재는 법이 재려는 것을 다 덮는가」**
  (CLAUDE.md §6-2-6 의 46 → 105 · §8 의 쪼개기 래칫과 **같은 규칙**이다.
  그때는 덜 세었고 이번엔 **더 세었다** — 방향만 다르고 잘못은 같다).

## 2부. 부딪히는 자리 — **앞 지시가 이긴다**

지침이 새것이라고 앞 지시를 덮으면, 사장님이 따로 적어 주신 것이 **조용히 사라진다**
(CLAUDE.md §12-2 와 같은 잣대).

### 2.1 낱말이 겹치는 자리 — **둘이 늘어 열하나가 됐다**

- ★★★ **「Gate / 단계 번호」 — 열째 겹침.** 이 지침은 §16 에서 **1~6단계**를 둔다.
  `RELEASE:Gate 3`(Staging) · `INSIGHT:Gate 3`(콘텐츠) · `BRIEF:Gate 3`(기능 E2E) ·
  `CAL:Gate 3`(기능) 과 **또 다르다.** **`CARD:1단계` … `CARD:6단계`** 로 부른다.
  **접두어 없는 「Gate 3」은 여전히 CLAUDE.md §11 것이다.**

- ★★★ **「연동」 — 열한째 겹침.** 이 지침의 「자동연동」은 **명함 ↔ 기기 연락처**이고,
  §6-2-4 의 「연동」은 **바깥 서비스 OAuth 이어짐**(캘린더·메일)이다.
  **접두어로 부른다**: `CARD:연동`(연락처) · `OAUTH:연동`(바깥 서비스).
  ★ 안 가르면 §6-2-4 의 「로그아웃으로 끊지 않는다」가 **연락처 권한에 그대로 적용되어**,
    사장님이 권한을 거두셔도 계속 동기화하는 코드가 된다 — 이 지침 §14 가 **금지**한 것이다.

### 2.2 앞 지시가 이기는 자리 — **셋**

| 지침이 말하는 것 | 앞 지시 | 어느 쪽을 따르나 |
|---|---|---|
| §15 `Validation Manager` 를 둔다 | **D-202 로 이미 미결**이다 | **없는 것을 있는 척 안 적는다.** 이름이 생긴 것이지 실체가 생긴 것이 아니다 |
| §13 화면 구성 | 보고서 자리의 머리는 **이쪽 화면이 단다**(§8-2) · UI 이모지는 **1단계 시안 대기**(§6-3) | 앞 지시 |
| §20 15번 「사용자 승인 전 …금지」 | CLAUDE.md §10 과 **같다** | 새로 만들지 않는다 |

### 2.3 ★★★ 이 지침이 **가장 세게** 못박는 것 — 옮겨 적는다

> **자동연동은 사용자 모르게 연락처를 읽거나 수정하는 기능이 아니다.** (§2.1)

기계가 **혼자 하는 것**: OCR · 전화번호 정규화 · 기존 연락처 검색 · 중복 가능성 판단 · 제안
사람이 **확인해야 하는 것**: 기기 연락처 생성 · 기존 연락처 변경 · 인맥정보 통합 · 연결 확정

★ 이것은 CLAUDE.md §4.9 「자동으로 하나를 고르지 않는다」와 **같은 규칙**이다.
  틀렸을 때 **그 사람의 연락처가 망가지고**, 되돌릴 수가 없다.

## 3부. 실행 규격 — **이 저장소의 일과를 바꾸는 것만**

### 3.1 전화번호 정규화 — **저장·검색은 국제형식 하나로**

- 저장·비교는 **`+8210…` 한 벌**로 한다. 화면에는 사람이 읽는 모양으로 보인다.
- ★ **원문을 버리지 않는다** — `raw` 와 `normalized` 를 **둘 다** 남긴다.
  버리면 「이 번호가 어디서 왔나」를 못 되묻는다 (§4.7 「무엇을 버리는지 본다」와 같은 결).
- ★★ **못 고치면 «고쳤다고 적지 않는다».** 자릿수가 안 맞거나 나라를 모르면
  `normalized:null` + 사유를 남기고 **검색에서 뺀다** — 억지로 맞추면 **남의 번호에 붙는다**.

### 3.2 중복 판단 — **자동으로 합치지 않는다**

- 전화번호 완전일치 → **연결 제안**. 이름+회사만 같음 → **후보로만 보인다.**
- ★★★ **서로 다른 인물을 자동통합하지 않는다** (§19 7번 · 장애 중요도 **HIGH**).
  헷갈리면 **둘 다 보여 주고 사람이 고른다.**
- ★ **검색 로그에 전화번호 원문을 안 남긴다** (§14). 가리는 것은 `SECRET_ENV` 가 아니라
  **이 갈래의 자기 규칙**이다 — 번호는 비밀값 목록에 없으므로 **코드가 직접** 가려야 한다.

### 3.3 기기 연락처 — **없는 길을 되는 척 그리지 않는다**

- ★★★ **웹에서 기기 연락처를 읽는 공개 창구는 «거의 없다».** `ContactsManager` 는
  안드로이드 크롬 일부에서만 돌고 **읽기 전용**이며, iOS 사파리는 **아예 없다.**
  지침 §7.3 이 그 제한을 적어 두었다.
- ★ 그러므로 **되는 길부터 적는다** — 내보내기(연락처 파일)와 딥링크로 **사람이 저장**한다.
  안 되는 것을 단추로 그리면 **눌러도 안 가는 것이 고장으로 읽힌다** (§8 · §6-2-5 와 같은 결).
- ★★ **권한을 거부해도 LinkPilot 안에는 저장된다** (§19 9번). 막다른 길을 만들지 않는다.

### 3.4 Source of Truth — **사본을 만들지 않는다**

- 인물 기본정보는 **인맥관리 엔진 한 곳**이 갖는다. 통화·일정·할일·프로젝트·딜은
  **`contact_id` 로 가리킬 뿐** 이름·번호를 각자 베끼지 않는다.
- ★ 베끼면 한쪽만 고쳐진다 — 이 저장소가 **일곱 번** 겪은 그 결이다 (§8-1 · §6-3 ⑥).
- ★★ **충돌하면 「최근 수정」이 아니라 「사용자가 승인한 값」이 이긴다** (§11.3).
  시각으로 이기게 두면 **기계가 사람을 덮는다.**

### 3.5 `CARD:1단계` 는 **실사이고, 지금 그것이 이 문서다**

지침 §16 의 1단계는 「현행 실사」다 — **1부가 그 산출물**이다.
★ 2단계(OCR·정규화)로 넘어가기 전에 **1.2 표의 `UNVERIFIED` 둘**을 재야 한다:
  비교·확인 화면이 명함 갈래인지 · 신뢰도가 낮을 때 어떻게 갈리는지.

### 3.6 완료조건 열다섯 중 **지금 못 재는 것 넷**

| # | 조건 | 왜 못 재나 |
|---|---|---|
| 10 | Android·iPhone 실기기 | **실기기가 있어야 한다** — 이 자리에 없다 |
| 14 | Validation Manager 독립 검증 | **실체가 없다** (D-202) — 만드는 손과 재는 손이 같다 |
| 15 | 사용자 최종 승인 | 사장님만 하실 수 있다 |
| 11 | 개인정보·권한 시험 | 권한 API 가 안 붙어 있어 **거부 갈래를 못 만든다** |

★ **못 잰 것을 통과로 적지 않는다** (CLAUDE.md §8 · 지침 §19 마지막 줄과 같은 뜻).

## 4부. Orchestrator 최종 실행명령

★ 아래 열다섯은 **사장님 원문(§20)** 이다. 각 줄 밑의 ★ 는 **이 저장소에서 그것이
  무엇을 뜻하는지**를 내가 붙인 것이다 — 원문을 고친 것이 아니다.

1. **현재 구현상태를 읽기 전용으로 확인하라.** ★ **했다 — 1부가 그 결과다.**
2. **다섯 낱말로 상태를 구분하라.** ★ **했다 — 1.2 표.** `UNVERIFIED` 둘이 남았다.
3. **기존 기능·데이터·디자인을 임의로 삭제·변경하지 마라.** ★ 명함 OCR·이미지 보관은
   **이미 도는 것**이다. 식별자를 놓는 일이 그것을 건드리면 안 된다.
4. **OCR 후 전화번호 정규화와 중복검색을 구현하라.** ★ `CARD:2·3단계` — **새로 만드는 일**이다.
5. **연락처 권한은 사용시점에 목적과 범위를 설명하고 요청하라.** ★ 미리 묻지 않는다.
6. **기존 연락처를 자동으로 덮지 말고 비교·연결·업데이트 화면을 주어라.**
   ★ **HIGH 장애의 자리다** — 덮으면 그 사람의 연락처가 망가진다.
7. **`contact_id` 로 통화·일정·할일·프로젝트·딜·보고서와 연결하라.** ★ 식별자가 **0회**다.
8. **전문 엔진마다 원본을 중복 저장하지 마라.** ★ §3.4.
9. **통화분석은 분석 → 저장 제안 → 사용자 확인 → 최종 반영 순서를 지켜라.**
10. **실기기에서 정상·중복·충돌·권한거부·오류를 검증하라.** ★ **여기서는 못 잰다** — 적어 둔다.
11. **개인정보·권한·로그·백업·복원·롤백을 검증하라.** ★ 검색 로그에 **번호 원문 금지**.
12. **모든 문제에 중요도·상태·영향·근거·담당자·조치·완료조건·목표일·승인여부를 기록하라.**
    ★ 자리는 `docs/미결정-사항.md` 의 관리대장이다 — **지금 12건 중 인계자·인수자가 전부 비어 있다.**
13. **같은 문제가 2회 이상이면 RCA 를 제출하라.**
14. **CRITICAL/HIGH 0건 · 핵심 시나리오 100% 통과를 확인하라.**
15. **사용자 승인 전 `main` 병합 · 운영배포 · 운영 DB 변경 · 연락처 변경 · 외부 공개 금지.**
    ★ CLAUDE.md §10 과 **같다.** 여기에 **「연락처 변경」이 더해졌다** — 그것이 이 지침의 몫이다.

### 보고 순서 (원문 그대로)

종합상태 → 한 줄 요약 → 구현현황 → 데이터 연결현황 → 신규 문제 → 미해결 CRITICAL/HIGH
→ 완료·검증 조치 → 우선조치 TOP 3 → 확인 불가 항목 → 사용자 결정·승인사항

## 6부. 최종 업무지시 (원문 §21)

> 이 기능의 핵심은 명함정보를 많이 저장하는 것이 아니라
> **한 사람을 정확히 식별하고, 기존 연락처를 보호하면서 LinkPilot 의 업무정보와 연결하는 것**이다.
>
> **정확한 인식 → 중복 확인 → 사용자 승인 → 안전한 연결 → 업무 활용**
>
> 편의성을 이유로 연락처 정확성·개인정보·사용자 통제권을 낮추지 않는다.
