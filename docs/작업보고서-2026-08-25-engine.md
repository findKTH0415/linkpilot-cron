### 3-1. Gemini 8-Key Manager 〈D-110〉 — 신규

사장님 작업지시서 「Gemini 6-Key Manager」에 따른 구현.

| 산출물 | 내용 |
|---|---|

| `core/llm.js` (개작) | 고르기를 위임하고 결과만 통보. 실패 분류 후 갈아타기 |
| `tools/gemini-doctor.js` | **실제 호출 검증** — `npm run gemini:keys` |
| `tools/build-gemini-dash.js` | 자체완결 상태 화면 — `npm run gemini:dash` |
| 라우트 5개 | `status` `metrics` `health-check-all` `health-check` `revalidate` |
| `test/gemini-keys.test.js` | 규칙 25개 (실제 호출 없음 — `fetch` 대체) |
| `deploy-nas.yml` | 열쇠 이름 15개 추가 · 실측 단계 1개 추가 |

**시험으로 고정한 동작**

- Round-Robin — 열쇠 3개에 9번 → 3·3·3
- 429 Failover — 첫 열쇠 429 → 다음 열쇠가 정상 응답 (사용자 노출 없음)
- 401/403 격리 — `INVALID` 로 풀에서 제외, 사람이 재검증 가능
- 5xx 재시도 — 같은 열쇠로 500ms·1s·2s, 이후 다른 열쇠. **열쇠를 폐기하지 않음**
- Cooldown 사다리 — 60 → 120 → 300 → 600초
- Recovery — 쉼이 끝나도 `ACTIVE` 가 아니라 `VALIDATING`(다시 물어봐야 함)
- 동시 요청 — 동시 100회 → 25·25·25·25
- 재시작 복구 — 통계를 **지문으로** 잇는다 (슬롯을 옮겨도 이력이 따라감)
- 보안 — 응답·상태파일·로그 어디에도 열쇠 글자 없음

### 3-2. 「넣었는데 안 실리는」 상태를 두 번 잡음

**① 열쇠 11개가 배포에 안 실리고 있었다** 〈MEMORY M-40〉

```
엔진이 아는 열쇠   22
배포가 싣는 열쇠   11   ← KEPCO_BIGDATA_KEY 가 여기 없었다
```

증상이 조용하다: 넣은 사람은 넣었다고 알고, 엔진은 「키가 없다」고 하고,
**배포는 초록으로 끝난다.** 세 진술이 모두 참이라 원인이 드러나지 않는다.

→ 배포 목록을 22개(현재 37개)로 맞추고, **두 목록이 같은지 검사가 고정**하도록 했다
(`secrets.test.js`). 커넥터를 붙이면서 배포 목록을 빠뜨리면 **그 자리에서** 빨개진다.

**② 열쇠 이름이 코드와 달랐다**

안내한 이름은 `GEMINI_KEY_01`, 실제 등록된 이름은 `GEMINI_API_KEY_2 … _8`.
그대로 두면 8개가 Secrets 에 있는데 엔진은 **1개만** 본다 — ①과 같은 증상.

→ **다시 등록을 요청하지 않고 코드가 두 이름을 모두 읽도록** 했다.
슬롯도 6 → 8 로 확장. 규격이 6이라는 이유로 이미 등록된 2개를 버리지 않는다.

**③ 곁가지 — Gemini 열쇠가 401 이었다**

열쇠 파일에 값이 있어 배포 로그는 「OCR 켜짐」으로 표시됐으나 실제 호출은
**HTTP 401**. 이 상태에서는 스캔본·이미지 PDF 가 한 글자도 안 읽히는데
**화면은 초록이고 문서도 나온다.** 사장님이 새 열쇠로 교체 → 확인 결과 살아남.

→ **교훈: 「값이 들어 있다」는 ACTIVE 의 근거가 아니다.** 배포에 실제 호출
검증 단계를 상설화했다.

### 3-3. 배포 중 화면이 깨지던 문제

**증상** 보고서 생성 화면 상단 붉은 띠 — 「화면에 필요한 파일을 못 받았습니다:
embed-bridge.js」. 데스크톱·모바일 동시.

**측정** 해당 파일은 NAS 에 존재하고 HTTP 200. 판 표시도 일치. 파일 문제 아님.

**원인** 배포가 파일을 **하나씩 약 70초에 걸쳐** 올린다. 그 사이 화면을 열면
HTML 은 새 판인데 형제 스크립트는 아직 옛 판이거나 없다.

**조치** 배포가 **형제(자산)부터 올리고 HTML 을 마지막에** 올리도록 순서 고정.
화면이 형제를 부르는 방향이므로, 형제가 먼저 자리에 있으면 그 창이 생기지 않는다.

**남는 창** 옛 화면이 새 형제를 부르는 짧은 구간은 남는다. 그쪽은 판 표시(`?v=`)와
짝 확인이 잡는다. **완전 제거는 §6-① 이 필요하다.**

**부수 개선** 빨간 띠가 **파일 이름만** 적어 「파일이 없다」와 「앱이 엉뚱한 자리를
본다」를 구분할 수 없었다 → **경로(pathname+search)** 를 적도록 변경. 호스트는 제거.

## 7. Orchestrator 가 알아야 할 구조적 제약 3가지

향후 작업 배분 시 이 셋을 어기는 지시는 이 저장소에서 **실행 불가**다.

1. **가정이 섞인 값은 자동 산출하지 않는다** (`CLAUDE.md §4.8`)
   일사량은 낸다 / 발전량은 안 낸다. REC·SMP 단가는 낸다 / 매출은 안 낸다.
   DSCR·IRR·EV/EBITDA·Synergy 는 **전부 가정계수를 품는다** — 계산은 하되
   `assumption: true` 로 표시하고 **사람 이름으로 채택**해야 한다.
   이 규칙이 무너지면 IM 의 숫자가 「우리가 만든 것으로 우리 주장을 증명하는」
   상태가 된다.

2. **MCP 서버를 붙일 수 없다** (`CLAUDE.md §5`)
   NAS 엔진은 단일 Node 프로세스다. MCP 클라이언트 + 별도 서버는 스택 변경.
   외부 소스는 **HTTP 커넥터**로 붙인다 — 이미 24개가 그 방식이고 캐시·재시도·
   마스킹·실패격리가 `connectors/http.js` 한 곳에 모여 있다.

3. **회계 장부와 딜 자료를 같은 저장소에 두지 않는다**
   Xero·hledger 는 PDI 의 장부이지 딜 자료가 아니다. 섞이면 「이 숫자의 출처가
   무엇인가」의 답이 두 갈래가 되고, 그것이 이 엔진이 지키는 유일한 규칙이다.
