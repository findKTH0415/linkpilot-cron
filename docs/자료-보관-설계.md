# 올린 자료를 서버에 보관하는 설계 — 리스크를 어디까지 줄였는가

작성 2026-08-17 (KST) · 등록부 **D-64** · 구현 `im-agent/core/vault.js`

> **한 줄:** 자료를 잃지 않게 만들고(덮어쓰기·잘린 파일·바꿔치기), 지울 수 있게
> 만들고(휴지통·되돌리기), **덜 보관하도록** 만들었다.
>
> 보관 리스크를 줄이는 가장 확실한 수단은 암호화도 백업도 아니고 **덜 보관하는
> 것**이다. 없는 파일은 새지 않는다.

---

## 0. 무엇이 문제였나 — 저장이 한 줄이었다

지금까지 올린 자료는 이렇게 저장되고 있었다.

```js
fs.writeFileSync(path.join(dir, name), buf);
```

그 한 줄에 **네 가지가 없었다.** 넷 다 증상이 조용하다는 공통점이 있다.

| | 없던 것 | 일어나는 일 | 왜 안 잡히는가 |
|---|---|---|---|
| ① | 덮어쓰기 보호 | 같은 이름을 올리면 **이전 파일이 사라진다** | 화면에는 「저장됨」만 뜬다 |
| ② | 원자적 쓰기 | 디스크가 차면 **잘린 파일이 최종 이름으로** 남는다 | 그 파일은 열리기는 한다 |
| ③ | 해시 | 파일이 바뀌어도 **증명할 방법이 없다** | 보고서는 그대로 나오고 출처 표시도 멀쩡하다 |
| ④ | 지우는 길 | 잘못 올린 자료가 **영구히 남는다** | 지울 방법이 없으니 아무도 안 지운다 |

③ 이 이 저장소에서 특히 무겁다. 시스템의 전제가 **「출처 없는 숫자는 들어오지
못한다」**인데, **그 출처가 되는 파일이 그때 그 파일인지 알 수 없으면 출처 표시는
반쪽**이다.

## 1. 무엇을 만들었나 — `core/vault.js`

```
02_Source_Data/                  살아 있는 원본
02_Source_Data/.vault.json       장부 — 지금 상태 (파일별 해시·크기·시각·올린 사람)
02_Source_Data/.vault-log.jsonl  기록 — 무슨 일이 있었는가 (덮어쓰지 않는다)
02_Source_Data/.trash/           휴지통 — 지운 것·덮어쓴 것
02_Source_Data/.tmp/             쓰는 중 (rename 전)
```

| 함수 | 무엇을 막는가 |
|---|---|
| `put()` | 덮어쓰기 · 잘린 파일 · 경로 조작 · 해시 없음 |
| `trash()` · `restore()` | 되돌릴 수 없는 삭제 |
| `purge()` | 실수로 도는 전체 삭제 (날짜 필수 · 기본이 미리보기) |
| `verify()` | 조용한 변조 · bit rot · 장부 밖 파일 |
| `reconcile()` | 「장부에 없으니 없는 것」으로 치는 일 |
| `usage()` | 용량이 어디로 갔는지 모르는 상태 |
| `reviewDue()` | 끝난 딜 자료가 영원히 남는 일 |
| `sweepTmp()` | 죽은 조각이 디스크만 먹는 일 |

### 원자적 쓰기 — 왜 이렇게까지 하는가

```
.tmp 에 쓴다 → fsync → rename
```

`writeFileSync` 는 디스크가 차면 **잘린 파일을 최종 이름으로 남긴다.** 그 파일은
열리기는 하는데 내용이 모자라고, 증상이 「원본이 이상하다」로만 보여 저장이
원인이라는 것이 드러나지 않는다. rename 은 같은 파일시스템 안에서 원자적이므로
**최종 이름은 다 쓴 파일로만 나타난다.** `.tmp` 를 같은 폴더 아래 둔 이유도
그것이다 — `/tmp` 에 두면 다른 파일시스템일 수 있어 rename 이 복사로 바뀐다.

### 덮어쓰지 않는다

같은 이름이 오면 **기존 파일을 휴지통으로 보내고** 새로 쓴다. 응답의 `replaced`
로 그 사실을 돌려준다 — 조용히 바뀌면 사용자는 옛 파일이 아직 있다고 믿는다.
**내용이 완전히 같으면 아무것도 하지 않는다** (같은 파일을 두 번 올리는 일은
흔한데, 그때마다 세대가 쌓이면 용량만 먹는다).

### 되돌릴 수 없는 동작에는 기본값을 두지 않는다

`purge()` 는 **`olderThanDays` 를 반드시 받고**, `dryRun` 이 **기본**이다.
기본값을 두면 「전부 지우기」가 실수로 도는데, 그 실수는 되돌릴 수 없다.

## 2. 붙이면서 찾은 것 — **버린 자료가 다시 실릴 참이었다**

`store.listSourceFiles()` 가 `02_Source_Data` 를 **재귀로 훑으면서 아무것도 거르지
않고** 있었다. 휴지통을 만들면 그 안의 파일이 그대로 추출 대상이 된다.

> **지운 자료가 다음 보고서에 다시 실린다. 지운 사람은 지운 줄 알고 있다.**

숨김 이름을 건너뛰게 고쳤다. 덤으로 `.DS_Store`·`._foo` 같은 macOS 부산물도 지금까지
추출 대상이었던 것이 빠졌다.

**그리고 건너뛴 것을 말하게 했다** (`listExcludedSourceFiles()`). 생성 로그에
「읽지 않음: .trash (3건, 812KB) — 휴지통이라 읽지 않습니다」가 남는다.
조용히 빠지면 「올렸는데 값이 안 뽑힌다」의 원인이 어디에도 안 남는다.

## 3. 하지 않은 것 — 그리고 그 이유

리스크를 줄인다고 아무거나 넣지 않았다. **넣는 것 자체가 새 리스크인 것들이 있다.**

| 안 한 것 | 왜 |
|---|---|
| **애플리케이션 레벨 암호화** | 키 관리가 새 리스크가 된다(§2 — 시크릿). **키를 잃으면 자료를 통째로 잃는다.** 볼륨 암호화가 맞는 자리다 (§4) |
| **파일명을 해시로 바꾸기** | 디렉터리 목록·백업에 딜 정보가 안 남는 대신, **NAS 에서 사람이 파일을 못 찾는다.** 운영이 망가지면 사람이 우회한다 |
| **자동 삭제** | 판단이 틀릴 수 있고 삭제는 되돌릴 수 없다. `reviewDue()` 로 **알리기만** 한다 |
| **확장자 화이트리스트** | 「읽지 못하는 형식도 저장하되 그렇다고 말한다」가 이미 내린 결정이다. 원본 보관 이유는 많다 |
| **바이러스 검사** | 새 의존성·새 데몬이다(§5). NAS 쪽 백신이 맞는 자리다 (§4) |
| **버전을 무한 보존** | 세대를 다 남기면 용량이 곱으로 는다. **직전 판만 휴지통에** 남기고 나머지는 보관 기간으로 관리한다 |

## 4. 코드로 못 막는 것 — **운영에서 해야 한다**

여기부터는 `vault.js` 가 손댈 수 없는 자리다. **적어 두지 않으면 안 한 채로
「보관 리스크를 줄였다」가 된다.**

| | 무엇 | 왜 코드가 못 하는가 | 지금 상태 |
|---|---|---|---|
| ① | **볼륨 암호화** (Synology 암호화 공유폴더) | 디스크가 반출되면 파일 권한은 아무 의미가 없다 | ☐ 미확인 |
| ② | **백업 — RAID 는 백업이 아니다** | 랜섬웨어·실수 삭제는 RAID 를 넘어 **복제된다** | ☐ 미확인 |
| ③ | **스냅샷 보존** (Btrfs) | 되돌릴 지점이 없으면 휴지통도 같이 암호화된다 | ☐ 미확인 |
| ④ | **원본 자료 내려받기 경로** | 지금은 없다. 붙일 때 `application/octet-stream` + `Content-Disposition: attachment` 여야 한다 — `.html` 원본을 인라인으로 열면 **그 안의 스크립트가 우리 도메인에서 돈다** | ☐ 아직 없음 |
| ⑤ | **접근 기록** (누가 언제 받았는가) | 유출 시 추적할 근거. `vault` 는 저장·삭제·복원까지만 기록한다 | ☐ 미결 |
| ⑥ | **한 프로세스로 운영** | `vault` 의 장부 갱신은 동기 구간이라 잠금이 없다. **프로세스를 여러 개 띄우면 전제가 깨진다** | ⚠ 확인 필요 |
| ⑦ | **보관 기간 정책 (일수)** | `reviewDue(days)` 의 `days` 를 정해야 동작한다 | ☐ 미결 |

**⑥ 이 가장 조용하다.** 장부가 어긋나도 파일은 멀쩡해서, 나중에 `verify()` 의
「장부 밖 파일」로만 드러난다.

## 5. 파일 권한

- 파일 `0o600` · 폴더 `0o700` — **소유자만.** NAS 공유폴더에 다른 계정이 있어도
  읽지 못한다.
- Windows 에서는 의미가 없지만 무해하다. 운영은 Synology(리눅스)다.

---

## 6. 용량과의 관계 (개정안 §3-1)

`usage()` 가 §3-1 이 세기로 한 것만 센다.

- **센다:** 올린 원본 + 휴지통
- **안 센다:** 생성 산출물 · API 캐시 — §6-1 이 SVG 마다 JPEG 을 하나 더 만드는데
  그것까지 청구하면 **규칙이 요금이 된다**
- `.tmp` 는 **청구에 안 넣되 합계에서 숨기지 않는다.** 숨기면 「사용량은 그대론데
  디스크가 찬다」가 된다

⚠ **일 스냅샷은 아직 안 찍는다.** §3-1 의 월 평균은 매일 재야 만들어지는데,
**안 재기 시작한 날부터의 과거는 나중에 만들 수 없다.** 스냅샷을 시작한 날이
청구 가능한 첫 달이 된다 — 등록부에 올렸다.

## 7. 새 엔드포인트

| | 무엇 | 비고 |
|---|---|---|
| `POST /projects/:id/sources` | 보관 | 기존 — 이제 `vault` 를 거친다 |
| `GET /projects/:id/sources` | 목록 · 휴지통 · 용량 | **볼 수 없으면 지울 수도 없다** |
| `DELETE /projects/:id/sources/:name` | 지우기 | **휴지통으로만** |
| `POST /projects/:id/sources/restore` | 되돌리기 | |
| `POST /projects/:id/sources/purge` | 휴지통 비우기 | `olderThanDays` 필수 · `confirm:true` 없으면 미리보기 |
| `POST /projects/:id/sources/verify` | 대조 | 저장할 때 남긴 해시와 지금 파일 |

**화면은 아직 없다.** 목록·지우기 UI 는 「자료」 탭(D-63)이 생길 때 붙는다 —
지침 재발행이 먼저다(개정안 §4). 서버 쪽을 먼저 만든 이유는 **지금도 자료를
받고 있기 때문**이다. 화면이 없는 것과 보관이 위험한 것은 다른 문제다.
