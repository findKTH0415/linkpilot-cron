# LinkPilot 정기 운영점검 및 보고지침

- 문서 버전: v1.0
- 제정일: 2026-08-30
- 적용 대상: `LinkPilot Orchestrator`, `linkpilot-platform`, `linkpilot-cron`, 전체 Agent, MCP/API, 프로젝트 DB, 디자인·보고서 출력체계
- 문서 목적: LinkPilot의 서비스·Agent·데이터·보안·비용·품질 상태를 매일·매주·매월 정기적으로 점검하고, 문제를 조기에 발견하여 담당자와 조치기한을 지정한다.

---

## 1. 운영 목표

정기 운영점검은 단순한 현황보고가 아니라 다음 결과를 만드는 것을 목표로 한다.

1. 서비스 중단, 데이터 손실, 보안 노출을 조기에 발견한다.
2. Orchestrator와 각 Agent의 성공률·지연·반복 실패를 확인한다.
3. 프로젝트 DB와 사용자 화면의 데이터 일치 여부를 검증한다.
4. 기능·디자인·문서 출력 품질을 함께 관리한다.
5. API·MCP 사용량, 장애, 비용 이상을 확인한다.
6. 발견된 문제마다 담당자·우선순위·완료기한·검증방법을 지정한다.
7. 사용자가 결정하거나 승인해야 할 사항을 명확히 구분한다.

## 2. 기본 운영원칙

1. 점검은 원칙적으로 읽기 전용으로 수행한다.
2. 증빙이 없는 항목은 정상 또는 완료로 추정하지 않는다.
3. 확인할 수 없는 항목은 `UNVERIFIED`로 표시한다.
4. 임시 데이터·Mock·하드코딩이 사용된 결과는 실제 운영 정상으로 판정하지 않는다.
5. 문제를 발견한 점검 Agent가 운영 코드를 직접 수정하지 않는다.
6. 수정은 Orchestrator가 담당 Agent에 별도 작업으로 배정한다.
7. 수정 후에는 실패 항목과 관련 기능의 회귀테스트를 수행한다.
8. `CRITICAL` 또는 `HIGH` 문제는 해결될 때까지 매일 재보고한다.
9. `main` 병합, production 배포, 운영 데이터 변경, 외부 공개는 사용자 승인 없이 실행하지 않는다.
10. 비밀번호·API 키·개인정보·계약정보를 보고서에 직접 노출하지 않는다.
11. 문제가 없더라도 `점검 완료 - 특이사항 없음`이라고 보고한다.
12. 보고서 생성 실패 또는 점검 미실행도 운영장애로 기록한다.

## 3. 권장 담당체계

### 3.1 Operations & Audit Manager Agent

독립적인 `LinkPilot Operations & Audit Manager Agent`를 정기점검 책임자로 지정한다.

주요 책임:

- 운영 증빙 수집
- 일일·주간·월간 보고서 작성
- 문제 중요도와 상태 판정
- 반복 장애와 추세 분석
- Orchestrator에 개선작업 등록 요청
- 사용자 승인·결정 필요사항 분리
- 미해결 문제의 후속조치 추적

금지사항:

- 운영 코드 직접 수정
- 운영 DB 직접 변경
- API 키 또는 비밀번호 출력
- 근거 없는 정상 판정
- 사용자 승인 없는 배포 또는 외부 공개

### 3.2 역할 분담

| 역할 | 책임 |
|---|---|
| Operations & Audit Manager | 읽기 전용 점검, 증빙수집, 정기보고, 문제 추적 |
| Orchestrator | 문제 분해, 담당 Agent 배정, 일정·의존성·승인 관리 |
| Platform Agent | 화면·백엔드·DB·API 관련 수정 |
| Engine/Engineering Agent | 분석·재무·도면·3D 등 전문 결과 수정 |
| Design Manager | UI/UX·문서·시각화·브랜드 디자인 검수 |
| QA/Validation | 기능·데이터·디자인·회귀검증 |
| 사용자 | 우선순위·예산·main 병합·운영배포·중대 변경 승인 |

## 4. 정기보고 일정

기준 시간대는 `Asia/Seoul`로 한다.

| 구분 | 실행시점 | 보고범위 | 권장 분량 |
|---|---|---|---:|
| 긴급보고 | 문제 발생 즉시 | 중단·보안·데이터·비용 중대 문제 | 핵심 5~10줄 |
| 일일보고 | 매일 08:30 | 직전 24시간 및 당일 우선조치 | 1페이지 |
| 주간보고 | 매주 월요일 08:30 일일보고에 추가 | 직전 7일 추세 및 금주계획 | 3~5페이지 |
| 월간보고 | 매월 첫 영업일 08:30 일일보고에 추가 | 전월 종합감사 및 개선계획 | 5~10페이지 |

월요일이 매월 첫 영업일에 해당하면 일일·주간·월간 내용을 하나의 통합보고서로 작성하되, 각 영역을 구분한다.

## 5. 공통 상태 및 중요도

### 5.1 운영상태

| 상태 | 의미 |
|---|---|
| `GREEN` | 정상, 즉시 조치 불필요 |
| `YELLOW` | 주의, 담당자와 완료기한 필요 |
| `RED` | 즉시 대응 또는 사용자 결정 필요 |
| `UNVERIFIED` | 자료·권한·증빙 부족으로 확인 불가 |

### 5.2 문제상태

- `NEW`: 신규 발견
- `ASSIGNED`: 담당자 배정
- `IN_PROGRESS`: 조치 진행 중
- `BLOCKED`: 권한·자료·의존성 문제로 중단
- `READY_FOR_TEST`: 수정 완료 후 검증 대기
- `TEST_FAILED`: 검증 실패
- `VERIFIED`: 증빙과 테스트 통과
- `CLOSED`: 최종 종료

### 5.3 중요도

| 중요도 | 기준 |
|---|---|
| `CRITICAL` | 서비스 중단, 데이터 손실·변조, 보안 노출, 복구 불가능 위험 |
| `HIGH` | 핵심 업무 불가, 주요 결과 오류, 반복 실패, 배포 차단 |
| `MEDIUM` | 일부 기능·품질·사용성·비용효율 문제 |
| `LOW` | 경미한 표시·정리·문서 문제 |

## 6. 긴급보고 기준

다음 문제는 정기보고 시점까지 기다리지 않고 즉시 보고한다.

1. 운영서비스 중단 또는 핵심 기능 사용 불가
2. 데이터 손실·변조·대량 불일치
3. 프로젝트 간 데이터 혼합 또는 권한 없는 열람
4. API 키·비밀번호·개인정보 노출 가능성
5. 비인가 코드 변경, `main` 병합 또는 운영배포
6. 백업 실패 또는 복원 불가능
7. Orchestrator나 핵심 Agent의 연속 실패
8. 프로젝트 DB와 화면 간 중대한 불일치
9. AI·API 비용의 비정상 급증
10. 보고서·계약서·재무분석 등 핵심 결과의 중대한 오류

## 7. 일일 운영점검

### 7.1 점검범위

#### A. 서비스와 인프라

- Platform 접속과 핵심 화면 정상 여부
- 서버·DB·스토리지·네트워크 상태
- 파일 업로드·다운로드·미리보기 정상 여부
- 모바일·Safari·Chrome 간 동기화 상태
- 예약작업과 `linkpilot-cron` 실행상태
- 전일 백업 성공 여부

#### B. Orchestrator와 Agent

- Agent별 작업 요청·성공·실패·대기·중단 건수
- 평균 처리시간과 장기 실행 작업
- 동일 작업의 반복 실패
- Orchestrator 업무배정 누락
- 승인 대기 및 기한 초과 작업
- Agent 결과물과 완료조건 일치 여부

#### C. 데이터

- 프로젝트 DB와 사용자 화면 표시값 일치
- `project_id`, `request_id`, `task_id`, `artifact_id`, `version` 연결
- 중복·고립·누락 데이터
- 데이터 갱신시간과 동기화 지연
- Mock·예시·하드코딩 데이터 사용 여부
- 원본자료·출처·기준일·신뢰도 연결 여부

#### D. API·MCP·비용

- 연결 성공·실패 및 인증오류
- 호출 제한과 잔여 사용량
- 지연시간과 재시도 증가
- API별 전일 사용량과 비용
- 전주 또는 기준치 대비 비정상 증가
- 장애 시 대체수단 사용 가능 여부

#### E. 기능·출력·디자인

- 핵심 기능 오류
- IM·Teaser·보고서·PPT·Word·PDF 출력 성공 여부
- 표·차트·지도·이미지 표시 오류
- 모바일 잘림·폰트·레이아웃 붕괴
- 로딩·빈 화면·오류·완료 상태 표시
- 기능검증과 디자인검증 미통과 항목

#### F. 보안·권한

- 비정상 로그인 또는 접근시도
- 사용자·Agent별 권한 오류
- 비밀정보·개인정보의 화면·로그 노출
- 외부 공유와 다운로드 권한 이상
- 승인되지 않은 운영환경 변경

## 8. 주간 운영점검

### 8.1 점검범위

- 전체 작업 완료율과 Agent별 성공률
- 평균·최대 처리시간과 지연작업
- 전주 대비 장애·오류·재시도 변화
- 반복 장애 TOP 5와 근본원인
- CRITICAL/HIGH 문제의 해결률과 평균 해결시간
- DB·화면·Agent 결과 데이터 일치율
- 기능·디자인·보고서 품질 검증 통과율
- 신규 기능·코드·설정·배포 변경내역
- 단위·통합·회귀 테스트와 빌드 결과
- API·MCP 가용성, 사용량, 비용 추세
- 보안·권한·비밀정보 관련 이상
- 백업 성공률과 복원 가능성
- 기술부채와 문서화 누락
- 금주 목표·담당자·완료기한
- 사용자 승인 및 의사결정 안건

## 9. 월간 종합점검

### 9.1 필수항목

1. 시스템·Agent·데이터 구조 변경사항
2. 서비스 가용성과 주요 장애 통계
3. 반복 장애의 근본원인과 재발방지 이행률
4. 프로젝트 DB 정합성과 장기 미동기화 데이터
5. 사용자·관리자·Agent 접근권한 재검토
6. API 키·인증서·비밀정보의 만료 및 교체계획
7. 개인정보·계약정보·투자정보 보호상태
8. 백업 성공률과 실제 복원시험
9. API·AI·스토리지·서버 비용 추세와 예산대비 차이
10. Agent별 성능·정확성·재작업률
11. 디자인 시스템·보고서 템플릿 일관성
12. 기술부채·미완료 작업·오래된 문서
13. 장애대응·배포·롤백 매뉴얼 최신성
14. 다음 달 개선과제와 사용자 승인사항

### 9.2 월간 필수 검증 게이트

- 백업 복원시험 통과
- 핵심 사용자 흐름 재현시험 통과
- Source of Truth와 공통 식별자 일치
- 주요 권한 재검토 완료
- CRITICAL/HIGH 미해결 문제의 책임자와 완료기한 확인
- 배포·롤백 절차 유효성 확인
- 핵심 문서 최신성 확인

## 10. 핵심 KPI

초기 기준치는 실제 운영 데이터를 2~4주 수집한 뒤 확정한다. 기준 확정 전 수치는 `잠정`으로 표시한다.

| 영역 | KPI 예시 |
|---|---|

## 11. 문제관리대장

모든 문제는 다음 형식으로 관리한다.

| ID | 발견일 | 영역 | 문제 | 중요도 | 상태 | 영향 | 원인 | 담당자 | 조치 | 완료조건 | 목표일 | 증빙 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

운영규칙:

- 담당자가 없으면 완료로 판정하지 않는다.
- 목표일이 없으면 계획으로 인정하지 않는다.
- 증빙과 재검증 없이 `VERIFIED` 또는 `CLOSED`로 변경하지 않는다.
- 같은 문제가 2회 이상 발생하면 근본원인 분석과 재발방지 과제를 등록한다.

- 사용자 권한·외부 공유정책의 중대한 변경
- API 키·인증서 교체로 서비스 영향이 예상되는 작업

- 계약·재무·법률 결과물의 최종 확정

## 13. 자동화 실행지침

### 13.1 실행주기

- 매일 한국시간 오전 8시 30분에 실행한다.

### 13.2 자동화용 Orchestrator 명령문

```text
LinkPilot의 운영상태를 읽기 전용으로 점검하고 정기 운영보고서를 작성하라.

실제 접근 가능한 로그, DB 상태, Agent 작업기록, 테스트 결과, 빌드 결과,
백업 기록, API·MCP 사용기록 및 비용자료만 증빙으로 사용하라.
확인할 수 없는 항목은 정상으로 추정하지 말고 UNVERIFIED로 표시하라.

매 실행마다 직전 24시간의 일일점검을 수행하라. 실행일이 월요일이면
직전 7일의 추세, 반복장애, 성과, 미해결 위험 및 금주 계획을 포함한
주간점검을 추가하라. 실행일이 해당 월의 첫 영업일이면 전월의 보안,
권한, 비용, Agent 성능, 데이터 정합성, 백업·복원, 기술부채 및 문서
최신성을 포함한 월간 종합점검을 추가하라.

모든 문제에 CRITICAL/HIGH/MEDIUM/LOW 중요도와
NEW/ASSIGNED/IN_PROGRESS/BLOCKED/READY_FOR_TEST/TEST_FAILED/VERIFIED/CLOSED
상태를 지정하라. 문제마다 영향, 근거, 담당자, 조치, 완료조건,
목표일과 사용자 승인 필요 여부를 기록하라.

CRITICAL 또는 HIGH 미해결 문제는 해결될 때까지 매일 다시 보고하라.
동일 문제가 두 번 이상 반복되면 근본원인 분석과 재발방지 과제를
요청하라. 점검 과정에서 코드, 운영 DB 또는 운영설정을 직접 변경하지
말고 Orchestrator가 담당 Agent에 별도 수정작업을 배정하도록 요청하라.

main 병합, production 배포, 운영 데이터 변경, 외부 공개 및 비용이
발생하는 작업은 사용자 승인 없이 실행하지 않는다.

최종 보고서는 종합상태, 한 줄 요약, 핵심지표, 신규 문제, 미해결
CRITICAL/HIGH, 완료·검증된 조치, 우선조치 TOP 3, 확인 불가 항목 및
사용자 결정·승인사항 순으로 작성하라. 문제가 없더라도
'점검 완료 - 특이사항 없음'이라고 명시하라.
```

## 15. 최종 완료기준

정기점검 체계는 다음 조건을 모두 충족해야 운영 완료로 판정한다.

2. 실행 성공·실패 기록이 남는다.
3. 실제 운영 증빙과 보고서 항목이 연결된다.
4. 확인 불가 항목이 정상으로 잘못 표시되지 않는다.
5. CRITICAL/HIGH 문제가 해결될 때까지 추적된다.
6. 문제마다 담당자·기한·완료조건이 지정된다.
7. 수정 후 회귀검증 결과가 기록된다.
8. 사용자 승인 필요사항이 자동실행 항목과 분리된다.
9. 보고서가 사용자가 확인할 수 있는 위치에 보관된다.
10. 신규 운영담당자가 별도 설명 없이 점검과 후속조치를 재현할 수 있다.
