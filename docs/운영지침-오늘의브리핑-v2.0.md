## 1. 개선 목적

오늘의 브리핑을 단순한 일정·업무 목록에서 **사용자가 아침에 오늘의 상황을 이해하고 바로 행동하는 개인 업무 관제화면**으로 개선한다.

브리핑은 다음 질문에 1분 안에 답해야 한다.

> **오늘 무엇을 먼저 해야 하고, 언제 출발하며, 누구에게 무엇을 확인하고, 어떤 결정을 내려야 하는가?**

사용성 목표:

- 3초 안에 오늘의 전체상황 파악
- 10초 안에 첫 일정과 출발시간 확인
- 30초 안에 첫 행동 선택
- 1분 안에 미팅·업무·프로젝트 준비 완료

## 2. 최종 정보구조

### 2.1 전체 표시순서

| 순서 | 섹션 | 사용자에게 답하는 질문 | 기본 노출량 |
|---:|---|---|---:|
| 1 | 오늘 한눈에 보기 | 오늘은 어떤 하루인가? | 한 줄+지표 4개 |
| 2 | 날씨·옷차림 | 무엇을 준비해야 하는가? | 현재지역+첫 방문지 |
| 3 | 일정·동선 통합 | 언제 어디로 출발해야 하는가? | 다음 일정 3건 |
| 4 | 미팅·통화 준비 | 누구에게 무엇을 확인해야 하는가? | 일정별 핵심 3줄 |
| 5 | 오늘 할 일 TOP 3 | 무엇을 반드시 끝내야 하는가? | 최대 3건 |
| 6 | 프로젝트·딜 판단 | 오늘 어떤 결정을 내려야 하는가? | 최대 3건 |
| 7 | 놓치면 안 되는 알림 | 무엇이 늦거나 위험한가? | 최대 3건 |
| 8 | 오늘의 인사이트 | 더 나은 판단과 관계를 위해 무엇을 할까? | 업무 1건+관계 1건 |
| 9 | 참고정보 | 추가로 확인할 것은 무엇인가? | 접힌 상태 |

### 2.2 핵심 개선 원칙

1. 일정과 동선을 분리하지 않고 하나의 시간축으로 통합한다.
2. 통화분석을 별도 목록으로 나열하지 않고 관련 일정·연락처·프로젝트에 연결한다.
3. 할 일은 전체 건수가 아니라 오늘 반드시 끝낼 TOP 3를 먼저 표시한다.
4. 프로젝트는 진행현황보다 오늘의 결정·확인·요청사항을 표시한다.
5. 장기 지연업무는 첫 화면을 반복 점유하지 않고 별도 상태정리 카드로 묶는다.
6. 관리자·관제·테스트·버전·JSON 오류문구는 일반 사용자 화면에 노출하지 않는다.
7. 모든 카드에는 다음 행동 버튼을 하나 이상 제공한다.

## 3. 모바일 첫 화면 구성

### 3.1 스크롤 전 필수정보

모바일 첫 화면에는 다음 네 가지가 보여야 한다.

1. 오늘 한 줄 요약
2. 최우선 업무 또는 긴급판단 1건
3. 날씨·옷차림
4. 첫 일정과 권장 출발시간

### 3.2 첫 화면 예시

```text
9월 13일 일요일 · 서울

오늘은 미팅 3건, 긴급업무 1건이 있습니다.
첫 일정은 10:30이며 차량 이용 시 09:40 출발을 권장합니다.

[긴급] 11시 전 제안서 가격조건 확정
[날씨] 18℃ / 최고 25℃ · 오후 비 60%
[준비] 얇은 재킷과 우산

[지금 할 일 확인]
```

### 3.3 모바일 화면규칙

- 본문 좌우 여백: 최소 16px
- 터치영역: 최소 44×44px
- 본문 글자: 최소 15px
- 핵심숫자와 출발시간은 본문보다 크게 표시
- 카드 하나에 주 행동 버튼은 1개만 강조
- 보조 행동은 더보기 메뉴 또는 보조버튼으로 배치
- 한 화면에서 좌우 스크롤 금지
- 사이드바와 하단 내비게이션 동시 노출 금지
- 긴 목록은 기본 접힘, 사용자가 펼쳐서 확인

## 4. 섹션 1 — 오늘 한눈에 보기

### 4.1 표시내용

- 오늘 날짜·요일·지역
- 미팅 건수
- 오늘 할 일 건수
- 긴급·지연 건수
- 오늘 결정할 프로젝트 건수
- 첫 일정 시작시각
- 첫 권장 출발시각
- 오늘의 핵심 판단 한 줄

### 4.2 한 줄 요약 생성규칙

형식:

> 오늘은 `[미팅 수]`, `[긴급업무 수]`가 있으며, `[가장 중요한 행동]`을 `[목표시각]`까지 처리해야 합니다.

예시:

> 오늘은 미팅 3건과 긴급업무 1건이 있으며, 오전 11시까지 제안서 가격조건을 확정해야 합니다.

### 4.3 요약 선정 우선순위

`안전·법적기한 → 오늘 마감 → 첫 일정 준비 → 이동시간 위험 → 프로젝트 결정 → 일반업무`

요약은 최대 2문장으로 제한한다. AI가 근거를 확보하지 못하면 사실정보만 조합하고 추정판단을 표시하지 않는다.

### 4.4 행동 버튼

주 행동: `지금 할 일 확인`

버튼을 누르면 최우선 업무 또는 첫 일정 준비카드로 이동한다.

## 5. 섹션 2 — 날씨·옷차림

### 5.1 표시정보

- 현재기온·체감기온
- 최고·최저기온
- 강수확률·예상 강수시간
- 미세먼지 또는 대기질
- 폭염·한파·강풍·호우·대설 등 기상특보
- 현재지역과 첫 방문지 날씨 차이
- 추천 옷차림과 준비물

### 5.2 행동형 표현

잘못된 예:

> 현재 18도, 최고 25도, 강수확률 60%입니다.

권장 예:

> 오후 비 가능성이 있습니다. 얇은 재킷과 작은 우산을 준비하세요.

### 5.3 옷차림 추천규칙

옷차림은 온도 하나가 아니라 다음 요소를 함께 반영한다.

- 체감온도
- 일교차
- 강수·적설
- 바람
- 실내·야외 일정 비중
- 격식 있는 미팅 여부
- 사용자가 저장한 선호

건강상태·질병을 임의로 추정하지 않는다.

### 5.4 날짜·음력·절기

날씨 카드 하단에 필요할 때만 한 줄로 표시한다.

- 양력·음력
- 윤달 여부
- 24절기
- 명절·공휴일·기념일
- 사용자가 등록한 특별한 날

공식 원문으로 확인되지 않은 날짜·기념일·날씨는 표시하지 않는다. 실제 기상정보를 계절상식보다 우선한다.

## 6. 섹션 3 — 일정·동선 통합 타임라인

### 6.1 기본 원칙

일정과 동선은 별도 섹션으로 만들지 않는다. 각 일정 카드 안에 이동정보를 함께 배치한다.

### 6.2 일정 카드 필수정보

| 구분 | 표시내용 |
|---|---|
| 일정 | 시간·제목·참석자·장소 |
| 이동 | 교통수단·예상시간·권장 출발시각 |
| 상태 | 정시·출발임박·지연위험·충돌 |
| 준비 | 준비자료·확인사항·최근 통화요약 |
| 행동 | 길찾기·미팅 준비·연락하기 |

### 6.3 카드 예시

#### 10:30 외제차량 수출 미팅

- 장소: 서울 강남구
- 차량: 42분 / 대중교통: 58분
- 추천: 차량
- 권장 출발: **09:40**
- 도착여유: 8분
- 주차: 건물 지하주차장
- 준비자료: 제안서·차량목록
- 최근 통화: 가격조건과 선적일정 재확인 요청

버튼: `길찾기` · `미팅 준비` · `연락하기`

### 6.4 권장 출발시각 계산

`권장 출발시각 = 일정 시작시각 - 실시간 이동시간 - 주차·도보시간 - 사용자 준비여유`

기본 준비여유:

| 일정 유형 | 기본 여유 |
|---|---:|
| 일반 약속 | 10분 |
| 중요 미팅 | 20분 |
| 공항·기차 | 교통수단별 별도규칙 |
| 온라인 미팅 | 접속·장비점검 10분 |

사용자가 여유시간을 직접 설정할 수 있게 한다.

### 6.5 교통수단 비교

- 차량·대중교통의 예상시간을 함께 표시한다.
- 비용·환승·주차·도보·교통상황을 반영한다.
- 추천 이유를 한 줄로 설명한다.
- 실시간 교통정보가 없으면 `예상시간`으로 표시하고 확정값처럼 표현하지 않는다.
- 출발지 또는 목적지가 없으면 사용자에게 입력을 요청하고 경로를 추정하지 않는다.

### 6.6 일정 충돌 처리

다음 경우 HIGH 알림으로 올린다.

- 앞 일정 종료부터 다음 일정 시작까지 이동시간이 부족함
- 동일 시간대 일정이 중복됨
- 목적지가 서로 다르지만 이동여유가 없음
- 출발시각이 현재시각보다 지남

## 7. 섹션 4 — 미팅·통화 준비

### 7.1 일정에 연결할 정보

- 마지막 통화일
- 통화 핵심요약
- 상대방 요청사항
- 아직 답하지 않은 내용
- 약속·합의한 내용
- 오늘 확인할 질문
- 관련 프로젝트·딜·문서
- 준비자료 누락 여부

### 7.2 미팅 준비 요약형식

```text
[최근 통화]
차량가격과 선적일정 재확인을 요청했습니다.

[오늘 확인]
계약금, 차량대수, 선적 가능일

[준비자료]
견적서, 차량목록, 계약조건표
```

### 7.3 통화분석 반영절차

통화분석 결과는 다음 순서를 지킨다.

`분석 → 저장 제안 → 사용자 확인 → 최종 반영`

- AI 요약을 자동으로 할 일·일정·프로젝트 원본에 저장하지 않는다.
- 사용자 확인 전 상태는 `PROPOSED`로 표시한다.
- 확정된 항목만 Source of Truth에 연결한다.
- 녹취 원문과 민감정보는 최소한으로 처리한다.

### 7.4 행동 버튼

- `미팅 준비`
- `질문 확인`
- `자료 열기`
- `연락하기`
- `할 일로 저장`

`할 일로 저장`은 사용자 확인 후 실행한다.

## 8. 섹션 5 — 오늘 할 일 TOP 3

### 8.1 분류

| 구분 | 의미 |
|---|---|
| 지금 해야 할 일 | 첫 일정 또는 가까운 마감 전에 처리해야 함 |
| 오늘 반드시 끝낼 일 | 오늘 완료하지 않으면 일정·계약·프로젝트에 영향 |
| 시간이 되면 할 일 | 긴급하지 않은 일반업무 |

### 8.2 우선순위 점수

| 항목 | 배점 |
|---|---:|
| 마감 긴급성 | 25 |
| 금액·법적·계약 영향 | 20 |
| 오늘 일정과의 연결 | 15 |
| 다른 업무의 선행조건 | 15 |
| 프로젝트 중요도 | 10 |
| 상대방 회신·약속 | 10 |
| 예상 소요시간 적합성 | 5 |

`업무우선점수 = 긴급성 + 영향 + 일정연결 + 선행조건 + 프로젝트중요도 + 회신약속 + 시간적합성`

AI는 점수와 추천 이유를 함께 저장한다. 사용자가 고정한 우선순위가 AI 계산보다 우선한다.

### 8.3 카드 필수정보

- 업무명
- 마감시각
- 중요도
- 예상 소요시간
- 관련 일정·프로젝트·상대방
- 추천 이유
- 바로 실행할 행동

### 8.4 장기 지연업무

86일 지연과 같은 오래된 업무를 매일 최상단에 반복 노출하지 않는다.

다음 상태로 재분류한다.

- 진행 유지
- 새 마감일 설정
- 담당자 위임
- 보류
- 완료
- 삭제 검토

표시 예시:

> **장기 지연업무 4건**  
> 실제 진행 여부와 마감일을 정리해야 합니다.  
> `상태 정리하기`

운영 데이터 변경은 사용자 승인 후 실행한다.

## 9. 섹션 6 — 프로젝트·딜 판단

### 9.1 표시원칙

전체 프로젝트 진행현황을 나열하지 않는다. 오늘 결정·확인·요청이 필요한 프로젝트만 최대 3건 표시한다.

### 9.2 필수정보

- 프로젝트명
- 현재 단계
- 오늘 필요한 판단
- 마감일
- 최근 변경사항
- 담당자·상대방
- 미회신·자료누락 여부
- 금액 또는 영향
- 다음 행동

### 9.3 예시

| 프로젝트 | 오늘 필요한 판단 | 다음 행동 |
|---|---|---|
| 자동차 수출 | 차량가격·선적 가능일 확정 | 견적 확인 |
| 태양광 사업 | 부지자료 누락 확인 | 담당자 요청 |
| 투자제안 | 투자자 회신기한 임박 | 연락하기 |

### 9.4 프로젝트 판단 생성원칙

- 통화·일정·할 일·딜 데이터를 공통 식별자로 연결한다.
- 원본 데이터를 브리핑 DB에 복제하지 않는다.
- 판단에는 근거 데이터와 기준시각을 연결한다.
- AI 추정은 `AI 제안`으로 표시한다.
- 금액·계약·법률 판단은 원문 확인 없이 확정하지 않는다.

## 10. 섹션 7 — 놓치면 안 되는 알림

### 10.1 통합 대상

- 오늘 마감
- 회신 없는 연락
- 결재 대기
- 계약·납부·제출기한
- 일정 충돌
- 이동시간 부족
- 통화 후 미반영 약속
- 준비자료 누락
- 장기 미처리
- 데이터 동기화 실패

### 10.2 노출규칙

- 중요도가 높은 순서로 최대 3건만 펼쳐서 표시한다.
- 나머지는 `알림 전체보기`에 접어 둔다.
- 동일 문제를 여러 섹션에 중복 표시하지 않는다.
- 해결된 알림은 즉시 첫 화면에서 제거한다.
- CRITICAL·HIGH 알림은 해결 또는 사용자 보류 전까지 재보고한다.

### 10.3 중요도

| 등급 | 기준 | 예시 |
|---|---|---|
| CRITICAL | 안전·개인정보·법적기한·대규모 손실 | 개인정보 노출, 오늘 법정기한 |
| HIGH | 오늘 일정·계약·핵심업무에 직접 영향 | 일정 충돌, 출발 지연, 필수자료 누락 |
| MEDIUM | 일부 지연 또는 품질저하 | 일반 회신 지연 |
| LOW | 참고 또는 향후 개선 | 단순 정리 필요 |

## 11. 섹션 8 — 오늘의 인사이트

오늘의 인사이트는 브리핑 전체를 가리는 대형 콘텐츠가 아니라 하루 판단과 관계를 돕는 두 개의 간결한 카드로 제공한다.

### 11.1 업무 인사이트

사용자의 일정·할 일·통화·프로젝트·딜을 연결해 오늘 필요한 판단을 한 문장으로 제시한다.

예시:

> 오전 미팅에서는 가격보다 차량 확보일과 선적 가능일을 먼저 확정하는 것이 좋습니다.

필수표시:

- 판단 근거
- 관련 일정 또는 프로젝트
- 생성시각
- 확신도 또는 `근거 부족`

### 11.2 소중한 사람에게 보낼 말

날씨·날짜·기념일·관계정보를 이용해 자연스러운 안부 또는 응원문구를 제안한다.

> 오늘 일교차가 크네요. 바쁜 하루겠지만 건강 잘 챙기세요.

버튼:

- `문장 만들기`
- `이름 넣기`
- `카카오톡으로 보내기`

자동발송은 금지한다. 사용자가 수신자와 내용을 확인한 뒤 전달한다.

### 11.3 AI 실패표시

사용자에게 JSON·스택·모델명·내부 오류를 보여주지 않는다.

권장 문구:

> 인사이트를 준비하지 못했습니다. 일정과 할 일은 정상적으로 확인할 수 있습니다.

버튼: `다시 시도`

## 13. 데이터 연결구조

### 13.1 연결 대상

| 데이터 | Source of Truth | 브리핑 사용목적 |
|---|---|---|
| 사용자·선호 | 내 정보 | 지역·출발지·여유시간·옷차림 선호 |
| 연락처·관계 | 인맥관리 | 참석자·연락·관계 인사이트 |
| 통화 | 통화분석 | 미팅 준비·미회신·약속 추출 |
| 할 일 | 할 일 관리 | TOP 3·지연·선행업무 |
| 일정 | 일정관리 | 타임라인·출발시각 |
| 프로젝트 | 프로젝트관리 | 오늘 판단·자료누락 |
| 딜 | 딜파이프라인 | 계약·금액·회신기한 |
| 투자 | 투자정보 | 관련 시장·기업 변화 |
| 에너지 | 에너지 사업분석 | 관련 정책·사업 리스크 |
| 문서 | 보고서 만들기 | 준비자료·최신본 링크 |

### 13.2 연결 원칙

- 모든 엔진은 `user_id`, `contact_id`, `task_id`, `event_id`, `project_id`, `deal_id`, `document_id`를 사용한다.
- 브리핑에는 원본 ID와 표시용 요약만 저장한다.
- 원본 수정은 각 전문 엔진에서 수행한다.
- 데이터가 삭제되면 브리핑 캐시에서도 제거한다.
- 충돌 시 Source of Truth의 최신 확정값을 사용한다.
- 화면과 DB 값이 다르면 정상으로 추정하지 않고 `UNVERIFIED`로 표시한다.

### 13.3 브리핑 객체 예시

```json
{
  "briefing_id": "brief_20260913_user001",
  "date": "2026-09-13",
  "timezone": "Asia/Seoul",

    "critical_task_count": 1,
    "first_event_at": "10:30",
    "recommended_departure_at": "09:40",
    "top_action": "제안서 가격조건 확정"
  },
  "weather_status": "VERIFIED",
  "schedule_status": "VERIFIED",
  "routing_status": "ESTIMATED",
  "generated_at": "2026-09-13T06:00:00+09:00",
  "refreshed_at": "2026-09-13T08:20:00+09:00"
}
```

### 13.4 일정·동선 객체 예시

```json
{
  "event_id": "evt_1001",
  "starts_at": "2026-09-13T10:30:00+09:00",
  "title": "외제차량 수출 미팅",
```

## 17. 필수 테스트

### 17.1 요약·우선순위

- [ ] 미팅·업무·긴급·판단 건수가 원본과 일치한다.
- [ ] 한 줄 요약이 2문장을 넘지 않는다.
- [ ] 최우선 행동의 근거가 표시된다.
- [ ] 완료한 업무가 상단에서 제거된다.

### 17.2 날씨·옷차림

- [ ] 현재지역과 방문지 날씨가 구분된다.
- [ ] 관측시각·예보시각·특보가 확인된다.
- [ ] 옷차림이 체감온도·일교차·강수와 일치한다.
- [ ] API 실패 시 계절상식을 실제 날씨처럼 표시하지 않는다.

### 17.3 일정·동선

- [ ] 일정 장소와 시간이 원본과 일치한다.
- [ ] 차량·대중교통 시간이 구분된다.
- [ ] 주차·도보·준비여유가 출발시각에 반영된다.
- [ ] 교통악화 시 출발시각이 갱신된다.
- [ ] 일정 충돌과 지연위험이 탐지된다.

### 17.4 통화·미팅 준비

- [ ] 최근 통화가 올바른 연락처·일정에 연결된다.
- [ ] AI 분석은 확정 전 `PROPOSED` 상태다.
- [ ] 사용자가 승인한 항목만 할 일·프로젝트에 저장된다.
- [ ] 민감한 녹취가 화면과 로그에 과도하게 노출되지 않는다.

### 17.5 할 일·프로젝트

- [ ] TOP 3 점수와 추천이유가 일치한다.
- [ ] 사용자 고정 우선순위가 AI보다 우선한다.
- [ ] 장기 지연업무가 별도 정리카드로 묶인다.
- [ ] 프로젝트에는 진행률보다 오늘의 판단이 먼저 표시된다.
- [ ] 관련 문서가 최신본으로 연결된다.

### 17.6 모바일·접근성

- [ ] 모바일 첫 화면에 4개 필수정보가 표시된다.
- [ ] 글자·카드·버튼이 잘리지 않는다.
- [ ] 터치영역이 최소 기준을 충족한다.
- [ ] 화면확대·키보드·스크린리더로 사용할 수 있다.
- [ ] 사이드바와 하단 내비게이션이 중복되지 않는다.

### 17.7 오류·보안

- [ ] JSON·스택·모델명·내부경로가 사용자에게 노출되지 않는다.
- [ ] 사용자별 데이터가 격리된다.
- [ ] 일정·통화·연락처 접근권한이 최소화된다.
- [ ] 로그에 민감정보 원문이 저장되지 않는다.
- [ ] 데이터 삭제가 브리핑 캐시에 반영된다.

최초 14일은 기준선 수집기간으로 운영한다. 임의의 목표치를 정상기준으로 확정하지 않는다.

## 19. 장애·이슈 관리

모든 문제에는 다음을 기록한다.

- CRITICAL / HIGH / MEDIUM / LOW
- 상태
- 사용자 영향
- 근거
- 담당자
- 조치
- 완료조건
- 목표일
- 사용자 승인 필요 여부

동일 문제가 2회 이상 반복되면 다음이 포함된 근본원인분석을 작성한다.

- 직접 원인
- 구조적 원인
- 탐지하지 못한 이유
- 임시조치
- 영구조치
- 재발방지 시험
- 담당자와 완료일

CRITICAL·HIGH 미해결 문제는 해결될 때까지 매일 보고하고 배포를 차단한다.

## 20. 릴리스 게이트

| Gate | 통과조건 |
|---|---|
| Gate 0 현행실사 | 코드·DB·API·Agent·화면 대응표 완료 |
| Gate 1 데이터 | 일정·통화·할 일·프로젝트 Source of Truth 정합성 통과 |
| Gate 2 날씨·동선 | 실제 날씨·교통·출발시각 검증 통과 |
| Gate 3 기능 | 요약·카드·버튼·저장·알림 E2E 통과 |
| Gate 4 콘텐츠 | AI 판단·문장·오류 대체화면 검수 통과 |
| Gate 5 실기기 | S22·iOS·Safari·Chrome·태블릿 통과 |
| Gate 6 보안·운영 | 권한·로그·백업·복원·롤백 통과 |
| Gate 7 사용자 승인 | 독립 검증보고 확인 및 운영배포 승인 |

사용자 승인 전 다음을 실행하지 않는다.

- `main` 병합
- Production 배포
- 운영 DB 변경
- 외부 공개
- 자동 메시지 발송
- 유료 API·광고 등 비용발생 작업

## 21. 완료 정의

다음 조건을 모두 만족해야 개선작업 완료로 판정한다.

1. 모바일 첫 화면에서 오늘 요약·긴급업무·날씨·첫 일정이 보인다.
2. 날씨가 옷차림과 준비물 행동으로 연결된다.
3. 일정마다 차량·대중교통·권장 출발시각이 표시된다.
4. 일정에 최근 통화·질문·준비자료가 올바르게 연결된다.
5. 할 일 TOP 3가 점수와 이유를 포함해 표시된다.
6. 장기 지연업무를 사용자가 상태 정리할 수 있다.
7. 프로젝트·딜 카드가 오늘의 판단과 다음 행동을 제시한다.
8. 동일 위험이 여러 영역에 중복 노출되지 않는다.
9. AI 실패 시 내부 오류 없이 핵심정보를 계속 사용할 수 있다.
10. 모든 화면값이 Source of Truth와 일치한다.
11. S22·iOS·Safari·Chrome 실제 기기시험이 통과한다.
12. 보안·백업·복원·롤백과 독립 검증을 통과한다.
13. 사용자가 최종 화면과 운영배포를 승인한다.

문서 작성, 샘플 데이터 화면, 프로토타입 배포만으로는 완료 처리하지 않는다.

## 22. Orchestrator 실행 프롬프트

```text
이 문서를 LinkPilot 오늘의 브리핑 v2.0 개선작업의 정본 실행지침으로 사용하라.

1. 기존 코드·DB·API·Agent·화면을 읽기 전용으로 실사하라.
2. 각 기능을 IMPLEMENTED / PARTIAL / DOCUMENTED / NOT IMPLEMENTED / UNVERIFIED로 분류하라.
3. 화면 순서를 다음과 같이 재구성하라.
   오늘 한눈에 보기 → 날씨·옷차림 → 일정·동선 → 미팅·통화 준비 → 할 일 TOP 3 → 프로젝트·딜 판단 → 놓치면 안 되는 알림 → 오늘의 인사이트 → 참고정보.
4. 모바일 스크롤 전 영역에 요약·긴급업무·날씨·첫 일정과 출발시간을 배치하라.
5. 일정과 동선을 통합하고 차량·대중교통·주차·도보·준비여유를 반영해 출발시각을 계산하라.
6. 통화분석은 관련 일정·연락처·프로젝트에 연결하고 분석 → 저장 제안 → 사용자 확인 → 최종 반영 절차를 지켜라.
7. 할 일은 오늘 반드시 끝낼 TOP 3를 먼저 표시하고, 장기 지연업무는 상태정리 카드로 분리하라.
8. 프로젝트는 전체 진행현황보다 오늘 필요한 판단·확인·요청·다음 행동을 표시하라.
9. 사용자 화면에서 관리자·관제·테스트·버전·JSON·내부 오류를 제거하라.
10. 원본 데이터를 복제하지 말고 공통 식별자로 Source of Truth에 연결하라.
11. 정상·지연·실패·근거부족·권한없음 상태를 모두 구현하라.
12. S22·iOS·Mac Safari·Desktop Chrome·태블릿에서 실제 기기 교차시험을 수행하라.
13. 모든 문제에 중요도·상태·영향·근거·담당자·조치·완료조건·목표일·승인 여부를 기록하라.
14. 동일 문제가 2회 이상 반복되면 RCA와 재발방지 과제를 제출하라.
15. 사용자 승인 전 main 병합·Production 배포·운영 DB 변경·외부 공개·자동발송·비용발생 작업을 실행하지 마라.

```

## 23. 최종 업무지시

오늘의 브리핑은 많은 정보를 보여주는 화면이 아니라 **오늘의 시간·사람·업무·프로젝트를 연결해 다음 행동을 알려주는 화면**이어야 한다.

모든 개발·디자인·Agent 작업은 다음 우선순위를 지킨다.

> **핵심 파악 → 출발 준비 → 미팅 준비 → 업무 실행 → 프로젝트 판단 → 위험 대응 → 인사이트**

정보량을 늘리기보다 사용자가 더 빨리 판단하고 행동하도록 개선한다.
