# 작업지침서 — SketchUp Engineering Agent 를 GitHub 에 붙여 쓰는 법

작성 2026-08-25 · 대상 저장소 `findKTH0415/linkpilot-cron` · 기준 판 `664b0bf8`

> **이 문서는 「붙이는 계획」이 아니라 「붙은 다음에 쓰는 법」이다.**
> 계획서는 [`작업지시서-스케치업-엔진-붙이기.md`](작업지시서-스케치업-엔진-붙이기.md)

> 무엇을 해야 하는지, 어디서 막히는지, 어떻게 확인하는지를 적는다.

## 0. 결론 — 먼저 세 줄

1. **엔진은 이미 붙어 있다.** Agent 가 11 → **13개**가 되었고, 배포 #107 이
   NAS 에 닿았다 (판 `664b0bf8`). 보고서를 만들면 SketchUp 계획이 **자동으로**
   나온다 — 아무것도 안 눌러도 된다.
2. **엔진은 SketchUp 을 부르지 않는다. 앞으로도 안 부른다.** SketchUp MCP 의
   모델 만들기는 **살아 있는 SketchUp 앱**에 명령을 밀어 넣는 방식인데,
   NAS 에도 GitHub 러너에도 그런 앱이 없다. 부르게 만들면 **「가끔 안 된다」**로
   깨진다 (D-95).
3. **그래서 사람 몫이 둘 남는다** — ① 맥북에서 모델을 만드는 일,
   ② 만든 결과를 프로젝트 폴더에 **돌려놓고 보고서를 한 번 다시 만드는 일.**
   ②를 빠뜨리면 화면은 계속 「결과 없음」이다. 여기가 가장 자주 막히는 자리다.

〈2026-08-25 추가 · D-104/D-105〉 두 가지가 더 들어간다.

- **`site.road_polygons_mm`** — 부지에 접한 도로필지. 연속지적도 bbox 1회 +
  토지특성으로 **지목 「도로」를 확인한 것만** 담고, 미확보면 `null` + notes 다.

`deliverables` 는 **4단계 출력조건에서 켠 시각자료**가 오는 자리다. 켠 것만
적히고, 근거(필지 형상)가 없으면 `blocked` 로 **왜 못 만드는지**가 함께 적힌다.

★ **엔진이 그 그림을 대신 그리지 않는다.** 엔진이 그리면 SketchUp 판과 두 벌이
되고, 그때 **어느 그림이 문서에 실렸는지 알 수 없게 된다.**

## 2. 한 번 돌 때 무슨 일이 일어나는가

보고서를 만들면 이 순서로 지나간다. 사람이 누를 것은 없다.

```
09_massing        매스를 세운다 (지상 8층 · 높이 36m)
   ↓
12_sketchup_plan  계획서를 쓴다 → 04_Property/model-plan.json
                  「시각자료 요청: 2건 (지적도면·조감도)」
   ↓
13_sketchup_intake 결과가 있으면 대조한다. 없으면 조용히 넘어간다
   ↓
05_validation     대조 결과가 값 검증에 합쳐진다
```

**결과가 없는 것은 오류가 아니다.** 평면 B 는 사람의 시간으로 도므로,
`13_sketchup_intake` 는 결과가 없으면 `unavailable` 로 끝내고 그 절을 비운다.

## 3. 사람이 하는 일 — 두 가지

### 3-1. 모델 만들기 (맥북)

절차는 [`스케치업-모델-만드는-법.md`](스케치업-모델-만드는-법.md) 에 일곱 단계로
적혀 있다. **여기서 되풀이하지 않는다** — 두 벌이 되면 한쪽이 옛말을 한다.

요약만 적으면: 맥북에서 Claude 를 열고 → 계획 파일을 붙여 넣고 → 모델을 만들게
시키고 → 눈으로 확인하고 → 저장하고 → 결과 기록을 만들게 하고 →
**파일을 프로젝트 폴더에 돌려놓는다.**

### 3-2. 결과를 돌려놓고 — ★ 보고서를 한 번 다시 만든다

**여기가 가장 자주 막히는 자리다.**

파일을 `04_Property/` 에 넣는 것으로 **끝나지 않는다.** 수령 Agent 는
**파이프라인이 돌 때** 그 폴더를 읽는다. 넣기만 하면 화면은 계속
**「결과 없음」**을 보여 주고, 그러면 사람은 **넣은 것이 잘못됐다고 읽는다.**

- 넣을 파일: `model-result.json` · `.skp` · 장면 PNG · (있으면) 렌더 이미지
- 넣은 뒤: **4단계에서 보고서를 한 번 다시 만든다.** 그때 대조가 돌고
  검증에 반영된다.

## 4. 확인하는 법 — 세 자리

### ① 저장소에서

`npm run guard` — 여섯 칸이 전부 초록이어야 내보낸다.
테스트 · 판 지문 · 미리보기 재생성 · 헤드리스 렌더 · [저장] 막대 자리 ·
[열기] 읽히는가.

`npm run im:demo` — 끝까지 돌려 보고 **세 줄**을 본다.

- `12_sketchup_plan … complete` 와 「모델 계획:」 줄
- 「시각자료 요청: N건」 줄 — 막힌 것이 있으면 그 까닭까지 적힌다
- `13_sketchup_intake … complete` — 결과가 없으면 조용히 지나간다

### ② 프로젝트 폴더에서

`04_Property/model-plan.json` 을 연다. `legal` · `objects` · `deliverables`
세 칸이 채워져 있는지 본다. 필지 형상을 못 받았으면
`site.parcel_polygon_mm` 이 `null` 이고 `notes` 에 **까닭이 적혀 있다.**

### ③ NAS 에서

배포가 스스로 잰다. `deploy-nas` 실행의 요약에서 두 줄을 본다.

- **「지적도: 켜짐」** — 실제 필지 형상으로 매스가 서고 조감도가 그려진다
- **「OCR: 켜짐」** — 스캔본·이미지를 글자로 옮겨 읽는다

★ **`npm run im:smoke` 로 운영 열쇠를 확인하지 않는다.** 열쇠는 GitHub Secrets 와
NAS 에만 있어서 저장소·개발 컨테이너에서 돌리면 **전부 「미설정」**이 나온다
(실측 `0/0 통과`) — **있는 것과 없는 것이 구분되지 않는다.** 스모크가 재는 것은
「이 커넥터가 응답을 제대로 읽는가」이고, 키가 있는 자리에서 돌려야 뜻이 있다.

## 5. 막히는 자리 — 다섯

| 증상 | 진짜 원인 | 어떻게 푸나 |
|---|---|---|
| 화면이 계속 「결과 없음」 | 파일만 넣고 **보고서를 다시 안 만들었다** | §3-2 |
| 바닥이 사각형이고 조감도가 없다 | `VWORLD_KEY`·`VWORLD_DOMAIN` 이 없다 | 고장이 아니다 — **근거 없는 그림을 안 그리는 것**이다. Secret 을 넣으면 다음 배포부터 켜진다 |
| 「계획을 내지 않았다」 (`PLAN_SKIPPED`) | 매스 검토가 **RED** 다 (용적률 초과 등) | 결측이 아니라 **판정**이다. 성립하지 않는 계획은 모델이 되면 안 된다 |
| 「계획을 만들지 않았다」 (`PLAN_MISSING`) | 매스 모델이 없다 (대지면적·층수·층고 중 하나가 빠졌다) | 그 값을 채운다. 반쪽 계획은 **반쪽인 것이 안 보인 채** 모델이 된다 |
| 렌더가 노란 딱지를 받는다 (`RENDER_DISCLAIMER`) | AI 렌더에 「실제 설계안이 아님」 표기가 없다 | 표기 없이는 문서에 안 싣는다 (D-34) |
| 렌더가 노란 딱지를 받는다 (`RENDER_TOOL_NONSTANDARD`) | 표준(Veras 4.0 · Nano Banana Pro 기반)이 아닌 도구·세대로 만든 렌더다 〈2026-08-25 사장님 지시 — 반드시〉 | 표준 도구로 다시 뽑는다. 무료 경로는 gemini + 같은 기반 모델만 통과한다 (규격 §3-1) |
| 배치도·3D 에 도로가 없다 | 도로필지를 못 받았다 (`road_polygons_mm: null`) | 고장이 아니다 — **지목을 확인 못 한 필지를 도로로 단정하지 않는 것**이다 (D-105). VWorld 열쇠가 있으면 다음 생성부터 실측 형상이 실린다. 예시 도로를 그릴 때는 화면에 예시라고 박는다 |

★ 위 일곱 중 **다섯은 고장이 아니다.** 근거가 없을 때 안 만드는 것이 이 저장소의
설계이고, 그때마다 **까닭이 계획서와 화면에 적힌다.**

## 6. Agent 를 하나 더 붙일 때 — 먼저 볼 것 둘

### 6-1. 이름과 번호를 **열려 있는 다른 갈래와 함께** 본다 ★★★

2026-08-25 에 실제로 이렇게 깨졌다 (D-101). 두 작업선이 같은 갈림점에서 나와
**같은 이름의 Agent 를 각자** 만들었고, **같은 파일을 쓰고 있었다.** 파일 이름이
같으니 병합은 **한쪽을 고르는 것으로 끝나고**, 진 쪽 설계는 **오류 하나 없이**
사라진다.

**번호를 비워 두는 약속으로는 못 막혔다.** 한쪽이 D-85~D-94 를 비워 뒀는데
다른 쪽이 그 뒤 번호를 또 땄고, 결국 여섯(D-96·D-97·D-98·D-99·M-33·M-34)이
두 뜻을 갖게 됐다.

- 새 Agent 이름·새 D 번호·새 M 번호를 딸 때 **열려 있는 PR 의 변경 파일을 본다**
- 부딪히면 **코드가 참조하는 쪽이 번호를 지킨다** (D-77 의 기준)

★★ **같은 날 두 번째로 깨졌다.** 이 절이 발행된 뒤에도 다른 작업선이
D-101·D-102 와 M-35 를 **자기 뜻으로 또 땄다** — 이 문서를 읽기 전에 번호부터
땄기 때문이다. D-104·D-105·M-50 으로 재번호해 풀었다. 교훈이 하나 더 붙는다:
**번호를 따기 전에 이 운용서와 열려 있는 갈래를 먼저 읽는다.** 읽지 않은
규칙은 없는 규칙이다.

### 6-2. 다섯 곳을 함께 고친다

§1-2 의 표 그대로다. 그리고 **가중치 합계 100** 을 지킨다 — 새 Agent 를 더할
때는 **어디서 덜어 올지 함께 정한다.** 합계가 100 이 아니면 검사가 잡는다.

### 6-3. 하지 않는 것

- **`facts` 를 내지 않는다** — 모델·계획에서 나온 수량은 **우리가 만든 값**이지
  근거가 아니다 (D-33 · D-96). 우리가 만든 값으로 우리 주장을 증명하면 안 된다.
- **엔진에서 SketchUp MCP 를 부르지 않는다** — 검사가 저장소 전체를 훑어 막는다.
- **같은 수를 두 곳에서 계산하지 않는다** (D-99).
