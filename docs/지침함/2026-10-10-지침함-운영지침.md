## 1. 목적
업무지침이 대화 속에만 남아 사라지지 않게 한다. 만든 지침은 다른 회사의 AI 가 한 번 더 보고, 프로젝트에 백업되고, Orchestrator 가 받아 반영한다.

## 2. 만드는 쪽 (프로젝트의 Claude)
1. 원본은 저장소 한 곳이다 — `docs/지침함/<YYYY-MM-DD>-<제목>.md`.
2. claude.ai 프로젝트 문서 `claude/지침함/<같은 이름>` 은 백업 사본이다. 사본 첫 줄에 «원본 경로 · 지문(12자리) · 백업 시각»을 적는다. 원본을 고치면 같은 턴에 사본도 새로 쓴다. 둘이 다르면 원본이 맞다.
3. 지침 머리에 지침 번호 · 판 · 작성 · 지시 · 적용 대상을 적는다.
4. 열쇠·비밀번호·전화번호·개인정보는 적지 않는다. 저장소가 공개다. 적혀 있으면 검증이 보내지도 커밋하지도 않는다.

## 3. 검증하는 쪽 (GitHub Actions · ChatGPT · Gemini)
1. 지침함에 글이 올라오면 워크플로 「업무지침 교차검증 (ChatGPT·Gemini)」이 저절로 돈다.
2. 검증은 차례대로 돈다. 1 Gemini → 2 ChatGPT(Gemini 의견을 받아 동의·반박) → 3 Claude(두 의견을 맞대어 정리)다.
   지침을 쓴 것도 Claude 라 독립 검증은 1·2번이다. 3번은 정리하는 자리다.
3. 열쇠가 없는 쪽은 건너뛴다. 그 칸은 현황표에 «검토 대기»(미확인)로 남는다. 통과로 적지 않는다.
4. 한쪽만 검토한 지침도 반영할 수 있다. 다만 반영기록 메모에 «단독 검증»을 적는다. 단독 판정이 «보완 필요»면 사장님 확인 뒤 반영한다. «반영 보류»는 4절 4항대로 반영하지 않는다.
5. 바뀐 지침만 검토한다. 지문이 같으면 다시 부르지 않는다.
6. 판정은 셋이다 — 통과 · 보완 필요 · 반영 보류. HIGH 문제가 있는데 «통과»라 온 판정은 «보완 필요»로 낮춰 적는다.
7. 검증 결과는 참고 의견이다. 승인이 아니다(CLAUDE.md §11).

## 4. 반영하는 쪽 (Orchestrator)
1. 세션을 열 때 `npm run guide:status` 로 현황표를 만든다.
2. «미반영»이면서 «통과»인 지침을 반영한다. 반영은 초안 PR 로 올린다.
   합치기는 CLAUDE.md §10 의 세 조건을 모두 채울 때만 한다. 검사 초록 · 겹친 나무 교차검증 · 잰 커밋 합치기다.
   운영 데이터 변경 · 외부 공개 · 새 유료 비용은 사장님 승인 뒤에 한다.
3. «보완 필요»는 사장님께 알리고 답을 받은 뒤 반영한다.
   알릴 때는 넷을 적는다. 어디서(화면·창) · 무엇을(고칠 점) · 어떻게(답하는 방법) · 그러면(답한 뒤 일)이다.
4. «반영 보류»는 반영하지 않는다. 까닭을 같은 넷으로 알린다. 지침을 고쳐 다시 올리면 다시 검토된다.
5. 반영하면 `반영기록.md` 에 한 줄을 적는다.
   파일 · 지문 · 반영 시각(Asia/Seoul, YYYY-MM-DD HH:mm) · PR 또는 커밋 · 한 줄 메모다.

## 5. 완료 조건
- 지침마다 검토 파일이 있고, 그 지문이 지침의 지금 지문과 같다.
- 반영한 지침은 반영기록에 지문이 있다.
- 백업 사본 첫 줄의 지문이 원본 지문과 같다.
- 기한: 검증은 지침이 올라온 그날 끝난다. 반영은 다음 Orchestrator 세션을 시작할 때 처리한다.
- 담당: 만들기·백업 = 프로젝트 Claude · 검증 = 워크플로 · 반영 = Orchestrator.
