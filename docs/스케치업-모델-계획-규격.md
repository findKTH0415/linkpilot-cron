# 스케치업 모델 계획·결과 규격

> **평면 A(엔진)와 평면 B(사장님 맥북)가 주고받는 파일 두 개의 규격이다.**
> 이 문서만 보고 사람이 손으로 `model-plan.json` 을 하나 쓸 수 있어야 한다 —
> 그것이 이 문서의 인수조건이다 (작업지시서 단계 1).

**근거**: [`작업지시서-스케치업-엔진-붙이기.md`](작업지시서-스케치업-엔진-붙이기.md) ·
등록부 **D-95**(맥북에서 사장님이 돌린다, 2026-08-24 결정) · **D-96**(모델 수량
fact 미등록, 2026-08-24 결정) · **D-33**(생성물은 fact 가 아니다) · **D-38**(형상
엔진을 서버로 세우지 않는다). 시각은 `core/kst.js` 의 `kstStamp()` 형식
(`2026-08-24T21:00:00+09:00`)을 그대로 쓴다 — 다른 형식을 만들지 않는다.

---

## 왜 파일 두 개인가

엔진(NAS·GitHub)에는 SketchUp 이 없고, SketchUp 쪽(맥북)에는 프로젝트
데이터베이스가 없다. 두 쪽이 직접 연결되면 **한쪽이 죽을 때 다른 쪽도 죽는다.**
그래서 파일 두 개로만 오간다:

| 파일 | 방향 | 뜻 |
|---|---|---|
| `model-plan.json` | 엔진 → 맥북 | 「무엇을 어디에 만들어라」 |
| `model-result.json` | 맥북 → 엔진 | 「이렇게 만들었다」 (+ `.skp`·PNG) |

두 파일 다 프로젝트 폴더의 **`04_Property/`** 에 둔다. `/SKETCHUP` 같은
새 폴더를 만들지 않는다 (D-74).

---

## 1. 단위 — mm 고정, 변환은 한 곳에서만

- **두 파일의 길이 값은 전부 mm 다.** 면적만 ㎡(`_m2` 접미사)를 쓴다.
- 엔진 내부(dataset·massing)는 m 를 쓴다 → **계획 Agent 가 plan 을 쓸 때
  한 번만** m→mm 로 바꾼다.
- SketchUp 은 내부적으로 inch 를 쓴다 → **맥북 세션(MCP 어댑터)이 받을 때
  한 번만** mm→SketchUp 으로 바꾼다.
- 그 밖의 어느 곳에서도 단위를 바꾸지 않는다. 변환 지점이 늘어날 때마다
  「백만 배 사고」(설계-협력사-산출물-규격의 mm 사고와 같은 것)의 자리가 는다.

## 2. `model-plan.json` — 계획

```json
{
  "schema": "model-plan/1",
  "project_id": "LP-DC-2026-001",
  "created": "2026-08-24T21:00:00+09:00",
  "units": "mm",
  "scale_status": "VERIFIED",
  "site": {
    "area_m2": 12500,
    "zoning": "일반공업지역",
    "far_limit_pct": 350,
    "bcr_limit_pct": 70,
    "source": { "fact": "land.area_sqm", "origin": "건축물대장" }
  },
  "building": {
    "floors": 4,
    "basement_floors": 1,
    "floor_height_mm": 4500,
    "footprint": { "width_mm": 60000, "depth_mm": 40000 },
    "gfa_m2": 9600,
    "source": { "fact": "building.gfa_sqm", "origin": "사업계획서" }
  },
  "objects": [
    {
      "object_id": "ROOM-003",
      "type": "room",
      "name": "DATA HALL A",
      "floor": 3,
      "x": 12500, "y": 8400, "z": 9000,
      "width": 28000, "depth": 18000, "height": 4500,
      "source": { "document": "A-203.pdf", "page": 17 }
    }
  ],
  "missing": [],
  "notes": []
}
```

- **`building` 의 층수·층고·건축면적은 09_massing 모델에서 그대로 옮긴다**
  〈2026-08-24 사장님 확인 — 계산 자리는 09_massing 하나다〉. 계획 Agent 가
  같은 수를 다시 계산하지 않는다 — 두 공식이 갈라지면 계획과 매스가 서로
  다른 건물을 말한다.
- **`site.parcel_polygon_mm` / `building.footprint_polygon_mm`** 〈2026-08-25 추가〉:
  `[[x,y], …]` mm 로컬좌표. 원천은 09_massing 이 지적도(VWorld)에서 만든 링이다 —
  **바닥은 이 필지 형상 그대로 그린다.** 지적선이 없으면 `parcel_polygon_mm` 은
  `null` 이고 notes 에 그 사실이 적힌다 (근사 형상을 실제 땅 모양처럼 그리지 않는다).
- **`legal`** 〈2026-08-25 추가〉: 법정 분석 동봉 — `far_limit_pct` ·
  `bcr_limit_pct` · `far_planned_pct` · `bcr_planned_pct` · `gfa_allowed_m2` ·
  `basis`(근거 법령) · `verdict`(`WITHIN_LIMITS` / `LIMIT_UNVERIFIED`).
  09_massing 검토값의 **표기용 사본**이다 — fact 가 아니다. 초과(RED)면 계획
  자체가 나오지 않으므로 `EXCEEDED` 는 이 파일에 존재하지 않는다.
- `objects` 는 **없어도 된다** — 대지·법정한도 기반 매스만으로 계획이 성립한다
  (도면 인식은 D-98 미결정). 있으면 항목마다 `source` 가 **필수**다.
- **자산군 개념 배치** 〈2026-08-25 사장님 지시〉: 자산유형이 아파트·주거·공동주택이면
  `objects` 에 `type: "building_bar"`(판상형 동)가 생성된다. **설계안이 아니라
  개념 배치다** — 판상형 깊이 13m·인동계수 0.8·폭 사용률 0.8 은 전부
  **통상치(ASSUMPTION)** 이고 확정은 D-100 이다. `source.origin` 과 notes 에
  그 사실이 박힌다. **objects 가 있으면 3D 는 단일 매스 대신 objects 를 올리고,
  `building` 블록은 법정 총량 검토값으로 남는다.** 어떤 값도 fact 가 되지 않는다.
- `source.fact` 는 dataset 의 키, `source.document` 는 원본 문서다.
  **출처를 적을 수 없는 객체는 계획에 넣지 않는다** (CLAUDE.md §4).

### 거절 규칙 — 계획을 내지 않는 경우

계획 Agent 는 아래 어느 하나면 **파일을 만들지 않고 사유를 남긴다.**
반쪽짜리 계획은 반쪽인 것이 안 보인 채 모델이 된다.

| 조건 | 처리 |
|---|---|
| 단위·축척을 확정 못 함 | `scale_status: "SCALE_UNVERIFIED"` 로는 **파일을 내지 않는다.** 경고 로그 + 그 절을 비운다 |
| **09_massing 모델이 없음** | `missing` 에 `massing.model` 을 적고 **계획을 내지 않는다** — dataset 값이 다 있어도 여기서 다시 계산하지 않는다 |
| 용적률 상한 초과 | 계획을 내지 않는다 — 09_massing 이 이미 RED FLAG 를 낸 상태다 |

## 3. `model-result.json` — 결과

맥북 세션이 모델을 저장한 뒤 쓴다 (마스터 프롬프트 §44 형식의 축약).

```json
{
  "schema": "model-result/1",
  "project_id": "LP-DC-2026-001",
  "plan_created": "2026-08-24T21:00:00+09:00",
  "created": "2026-08-25T10:30:00+09:00",
  "units": "mm",
  "model": {
    "floors": 4,
    "gfa_m2": 9600,
    "objects_count": 1,
    "components_count": 0
  },
  "validation": {
    "clean_geometry": "PASS",
    "solid": "SKIPPED_MASSING",
    "errors": []
  },
  "files": ["project.skp", "scene_001.png", "scene_002.png"],
  "scenes": [
    { "scene_id": "SC-001", "file": "scene_001.png", "label": "부지 전경" }
  ],
  "renders": [
    {
      "file": "render_SC-001_veras_01.png",
      "tool": "veras",
      "tool_version": "4.0",
      "engine": "Nano Banana Pro",
      "based_on": "SC-001",
      "settings": { "geometry_override": "낮음", "prompt": "재질·주변만, 형태·층수·비례 유지" },
      "ai_generated": true,
      "disclaimer": "AI 렌더 — 실제 설계안이 아님"
    }
  ],
  "status": "PASS",
  "unresolved": []
}
```

- `plan_created` 는 **받은 계획의 `created` 를 그대로 복사한다** — 수령 Agent 가
  「어느 계획에 대한 결과인가」를 이것으로 맞춘다. 다르면 옛 계획의 결과다.
- `validation.solid` 는 셋 중 하나: `PASS` / `FAIL` / `SKIPPED_MASSING`.
  **매스라서 건너뛰었으면 건너뛰었다고 적는다** — 조용히 빠지지 않는다.
- 수령 Agent(단계 4)는 `model` 의 층수·연면적·객체 수를 계획과 대조하고,
  어긋나면 YELLOW/RED 를 `05_validation` 에 넘긴다. `.skp`·PNG 는
  **있다는 사실만** 기록하고 파싱하지 않는다.
- **`model` 의 값은 fact 로 등록하지 않는다** (D-96 권고). 검토 결과로만 쓴다.

### 3-1. `renders` — AI 렌더(Veras 등)의 규칙

사실적 렌더(사장님이 Veras 로 만든 그림)는 `renders` 에만 넣는다. 규칙은
**D-34 결정을 그대로** 잇는다:

- `ai_generated: true` 와 `disclaimer` 는 **필수다.** 수령 Agent 는 disclaimer
  가 없는 렌더를 받으면 **YELLOW 플래그**를 낸다 — AI 그림이 설계안으로
  읽히는 것이 이 파일에서 막아야 할 사고다.
- `based_on` 에 원본 장면(SC-xxx)을 적는다 — 어느 뷰에서 나온 그림인지가
  출처다. 장면 없이 만든 그림은 받지 않는다.
- **`tool` + `tool_version` 도 필수다** 〈2026-08-25 — Veras 4.0 반영〉.
  같은 Veras 라도 세대마다 그림이 다르다 (4.0 은 Nano Banana Pro 기반) —
  어느 도구의 어느 세대가 만든 그림인지가 §4.7 의 출처 표기와 같은 결이다.
  없으면 수령 Agent 가 `RENDER_TOOL_UNKNOWN` YELLOW 를 낸다.
  `engine`(기반 모델명)과 `settings`(형상 유지 슬라이더 값·프롬프트)는
  **재현 조건**이므로 적기를 권장한다 — 같은 그림을 다시 만들 길이 이것뿐이다.
  Gemini 앱 무료 경로는 `tool: "gemini"` · `engine: "Nano Banana Pro"` 로 같은
  규격을 따른다.
- 파일명은 `render_<장면ID>_<도구>_<번호>.png` 로 한다.
- **쓰는 곳은 표지·티저다. IM 본문에는 싣지 않는다.** 본문 조감도는 지적선
  기반 `birdseye.js` 가 담당한다 (D-34 — 「모든 선이 지적도와 건축개요에서
  나온다」). 렌더의 어떤 값도 fact 가 되지 않는다.

## 4. 신뢰도 환산표 — 척도를 새로 만들지 않는다

마스터 프롬프트 원안의 백분율 밴드는 이 저장소의 A~E 등급
(`core/confidence.js`)으로 환산해서 쓴다. 두 척도를 병행하지 않는다.

| 원안 백분율 | 이 저장소 | 뜻 |
|---|---|---|
| 95~100 HIGH | **A** | 공적장부·검증된 값 |
| 85~94 MEDIUM-HIGH | **B** | 신뢰할 수 있는 단일 출처 |
| 70~84 MEDIUM | **C** | 문서 기반 추정 — `[추정]` 표기 |
| 50~69 LOW | **D** | 통상치·가정 — `[가정]` 표기 |
| <50 UNRELIABLE | **E** | 출처 미확인 — **본문 사용 금지** |

## 5. 손으로 써 보는 예시

[`docs/model-plan.sample.json`](model-plan.sample.json) 이 이 규격대로 손으로
쓴 완결 예시다 — **예시 데이터임이 파일 안에 적혀 있다.**
(`im-agent/samples/` 에 두지 않는다 — 그 폴더는 데모 파이프라인이 **원본자료로
읽어들이는 곳**이라, 예시 계획의 숫자가 추출 후보로 잡혀 실제 값과 섞인다.
실제로 넣었다가 계보 테스트가 잡아냈다.) 맥북 절차서
([`스케치업-모델-만드는-법.md`](스케치업-모델-만드는-법.md))의 첫 연습은
이 파일로 한다. 실제 계획은 `12_sketchup_plan` Agent 가 `im:demo`/파이프라인
실행에서 자동으로 낸다 — 예시는 규격을 손으로 검증하고 첫 연습을 하는 용도다.
