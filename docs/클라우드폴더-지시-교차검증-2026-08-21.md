## 2. 🔴 충돌 넷 — **반영하지 않았다**

### D-72 「폴더 연결 + 주기 감시」 vs **chooser 결정** 🔴

지시 §2(마지막 동기화 시간·연결상태) · §9(주기적 확인 → CHANGE DETECTED) ·
§10(자동 재검증)은 전부 **폴더를 계속 붙들고 지켜보는 것**을 전제한다.

**그런데 D-69 에서 사용자가 「그때그때 고르기(chooser)」로 결정했다** — 이유가
`refresh token 을 보관하지 않는다` 였다. 폴더를 지켜보려면 **토큰을 보관해야 한다**
(`connectors/storage.js` 의 `MODES.folder.keepsToken = true`).

| | chooser (지금 · D-69 결정) | 폴더 연결 (지시서가 요구) |
|---|---|---|
| 토큰 보관 | **안 한다** | **한다** — 새면 그 범위 전체가 샌다 |
| 새 파일 자동 인지 | 못 한다 | 한다 |
| 사용자 부담 | 자료 늘 때마다 다시 고른다 | 한 번 승인 |

**되돌릴 수 없는 쪽이 있다** — Dropbox 앱 타입은 한 번 정하면 앱을 다시 만들어야
바꾼다 (`storage.js` 의 `scopeNote`).

### D-73 결과물을 **클라우드 Output Folder 에 저장** 🔴

지시 §14 는 결과물을 `11_최종본` 에 저장하라고 한다. 지금 엔진은 남의 드라이브에
**쓸 권한이 없다.** chooser 는 고른 파일 하나에 대한 **읽기** 단발 접근권만 받는다.

쓰려면 범위를 넓혀야 하고, 그것은 **§4.5 「폴더까지만 받는다」 결정과 부딪힌다.**

### D-74 폴더 체계가 **두 벌**이 된다 🔴

| | 지시서 §3·§14 | 엔진 실제 |
|---|---|---|
| 원본 | `01_원본자료` | `01_Project` |
| IM | `08_IM` | `09_IM` |
| 최종 | `11_최종본` | `12_Final` |
| 검증 | `12_검증자료` | `11_QC` |

**번호가 겹치면서 뜻이 다르다** — `11` 이 한쪽은 최종본, 한쪽은 검증이다.
섞으면 어디에 저장됐는지 사람이 못 찾는다.

### D-75 작업지시를 **누가 만드는가** 🔴

지시 §5·§13 은 Agent 가 WORK ORDER 를 만들고 담당자를 지정하라고 한다.
지금 엔진에는 **작업·담당자·마감 개념이 아예 없다** — 프로젝트와 산출물뿐이다.
앱(딜파이프라인)에 그 자리가 있는지, 엔진이 가져야 하는지가 안 정해졌다.

## 4. ⭐ 이번에 반영한 것 — §7 최신 파일·버전 관리

**충돌이 없다.** 지시 §7 의 「Final 이라는 이름만으로 최신이라고 단정하지 않는다」는
CLAUDE.md §4.9 「자동으로 하나를 고르지 않는다」와 **같은 말**이다. 그래서 바로 붙였다.

`ui/platform/versions-core.js` — 화면과 Node 가 **같은 파일**을 쓴다.

```
IM_v1.pdf · IM_v2.pdf · IM_20260820.pdf · IM_Final.pdf · IM_Final_20260820.pdf
  → 한 묶음으로 잡고, 순서와 **근거**를 함께 보여 준다
  → 「무엇이 최신인지 가릴 근거가 없습니다 — 파일을 열어 확인해야 합니다」
```

### 지시서와 **다르게** 한 곳 하나 — 밝혀 둔다

지시 §7 의 우선순위는 `① 판 번호 ② 최종 표시 ③ 날짜 ④ 수정일` 이다.
그대로 옮겼더니 **`IM_Final.pdf` 가 `IM_v2.pdf` 를 앞질렀다.**

같은 지시서가 「Final 이라는 파일명만으로 최신본이라고 단정하지 않는다」고도
말한다. 두 줄이 서로 부딪힌다. **잴 수 있는 근거를 앞에 두는 쪽**으로 정했다:

```
판 번호 > 이름의 날짜 > 수정 시각 > 「최종」이라는 주장
```

그리고 **근거 종류가 다르면 가리지 않는다.** `IM_v2.pdf` 와 `IM_20260820.pdf`
중 무엇이 최신인지는 알 방법이 없다 — 순서는 보여 주되 「못 가렸다」고 말한다.
여기서 하나를 고르면 그것이 곧 추측이다.

- 화면: 「자료 붙이기」 목록 **위**에 뜬다. 아래에 두면 목록에서 아무거나 골라
  쓴 뒤에 보게 된다.
- 출처를 가리지 않는다 — Dropbox·NAS·앱이 넘긴 것을 **한 묶음으로** 본다.
  묶는 기준이 이름이지 저장소가 아니기 때문이다.

## 5. 「어떤 클라우드를 쓰더라도 동일한 방식」 — 지금 어디까지 되나

지시서의 이 요구는 **이미 구조로 되어 있다.** 저장소가 무엇이든 같은 길로 간다:

```
참조 받기(normalizeRef) → 장부(refKey) → 읽기(materialize) → 지문(sha256) → 출처(citation)
```

`connectors/storage.js` 는 저장소마다 다른 것(`versionField`·`hashKind`·범위)만
표로 들고 있고, **그 위의 처리는 전부 같다.** 그래서 저장소를 더해도 파이프라인은
안 바뀐다.

| 저장소 | 지금 | 남은 것 |
|---|:--:|---|
| Dropbox · Box · Google Drive · OneDrive/SharePoint | 표에 있다 | **콘솔 등록 4곳** (앱 몫) |
| **NAS** | 앱이 넘기는 경로(`linkpilot-app`)로 **이미 들어온다** — 본체가 `files.php` 를 https 로 서빙한다 | 사용자가 NAS 폴더를 **직접 고르는** 길은 없다 (고르기 창이 없다) → D-72 와 함께 정한다 |
| 기타 API 클라우드 | 표에 한 줄을 더하면 붙는다 | 그 저장소의 `versionField`·`hashKind`·범위를 정해야 한다 |

★ SharePoint 는 이미 `onedrive` 항목이 함께 맡는다 (이름이 `OneDrive · SharePoint`).

## 6. 그래서 다음은

1. **D-72 를 먼저 정한다.** 폴더 연결로 가느냐(토큰 보관) chooser 로 남느냐 —
   §9 감시·§10 재검증·§14 저장·NAS 직접 고르기가 **전부 여기에 매달려 있다.**
2. D-74(폴더 체계)는 D-73 이 「클라우드에 저장한다」로 정해질 때만 필요하다.
3. D-75(작업지시)는 앱 딜파이프라인과 겹치는지 먼저 봐야 한다.

★ 정해지기 전까지 **반쯤 만들지 않는다.** 「되는 것 같은데 안 되는」 상태가
가장 비싸다 (D-70 과 같은 태도).
