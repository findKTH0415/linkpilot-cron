## 2. 🔴 정정 셋 — **문서가 아니라 실물이 맞다**

### 2-1. **D-번호가 서로 다른 것을 가리킨다** — 가장 위험하다

본체 문서 §7 은 결정 3건을 `D-71 · D-69 · D-72` 로 부른다. 그런데 **엔진
등록부의 같은 번호는 다른 내용**이다.

| 본체 문서가 부른 이름 | 본체가 말한 내용 | **엔진 등록부에서는** |
|---|---|---|
| D-71 | Free 403 이 자료 탭 전체를 잠근다 | **D-71** — 같다 ✔ |
| D-69 | 폴더 연결 모드 = 토큰 보관 승인? | **D-72** (D-69 는 그 앞 결정) |
| D-72 | 클라우드 **쓰기** 개방? | **D-73** |

★★ **이름으로 맞추면 반대로 반영된다.** 「D-72 를 닫는다」를 본체 뜻(쓰기 금지)으로
읽고 엔진 D-72(폴더 연결)를 닫으면, **이미 사용자가 승인한 결정을 되돌린다.**

**맞추는 규칙 — 번호가 아니라 내용으로 잇는다.**

```
토큰을 보관하는 폴더 연결을 켤 것인가   → 엔진 D-72   (본체 문서는 「D-69 재확인」)
남의 클라우드에 결과물을 쓸 것인가      → 엔진 D-73   (본체 문서는 「D-72」)
Free 계정이 자료 탭에서 무엇을 보는가   → 엔진 D-71   (양쪽 같다)
```

★ 엔진 등록부는 **뒤집힌 결정을 지우지 않고** 「옛 결정」으로 남겨 두었다.
무엇을 왜 뒤집었는지가 남아야 하기 때문이다. 그래서 D-72 항목이 둘로 보인다 —
위가 지금 것, 아래가 옛 것이다.

### 2-2. **화면이 옛 판인 이유** — 배포 길이 **둘**이다

본체 문서는 현재 상태를 「엔진 NAS `95f81a5`」로 적었다. **그 판정은 맞다.**
그런데 같은 시각에 화면은 **여러 판 뒤처진 것**이 떠 있다. 모순이 아니다 —
**엔진과 화면은 서로 다른 길로 올라간다.**

| 무엇 | 어디로 | 누가 올리나 |
|---|---|---|
| **엔진 API** (8181) | `/volume1/docker/linkpilot/im-agent/` | `npm run deploy:nas` (엔진 저장소) |
| **화면 사본** (`im-flow/` 16파일) | 웹루트 `im-flow/` | `npm run im:embed` → **앱 저장소** → `deploy-filestation.py` |

`deploy:nas` 는 `im-agent` 만 말아 올린다 — **웹루트를 건드리지 않는다.**
그래서 **엔진만 올리면 화면은 그대로다.** 본체 문서 §6 의 표준 절차가
`deploy:nas` **와** `im:embed` 재빌드를 **둘 다** 적어 둔 이유가 이것이다.

> ★ 이 저장소 쪽에서 「화면이 안 바뀐다」를 배포 전체의 문제로 말한 적이 있다.
> **틀린 진단이었다.** 엔진은 최신인데 화면 사본만 안 만든 것이다. 화면을
> 고쳤으면 **`im:embed` 를 다시 돌려야** 웹루트로 갈 물건이 생긴다.

**화면만 반영하는 최단 경로** (엔진 재배포 불필요):

> ★★ **아래 `<…>` 는 자리표시가 아니다 — 실제로 칠 수 있는 줄이다.**
> 앞선 판에는 `--out <앱 폴더>/im-flow` 라고 적었고, 받은 사람이 **그대로**
> 붙여 넣어 셸이 죽었다. 자리표시를 남기지 않는다. 대신 **경로를 한 번만
> 정해 두고** 그 뒤로는 이름으로 부른다.

```bash
# ── 0) 앱 저장소가 어디인지 한 번만 정해 둔다 (~/.zshrc 에 넣어 두면 계속 쓴다)
export LP_APP_DIR="$HOME/…/24.홈페이지"      # ← 자기 앱 저장소 경로로 바꾼다
[ -d "$LP_APP_DIR" ] && echo "찾았다: $LP_APP_DIR" || echo "경로가 틀렸다"

# ── 1) 엔진 저장소에서 — 사본을 앱 폴더로 낸다
cd ~/linkpilot-cron
npm run im:embed                              # LP_APP_DIR 을 보고 im-flow 로 낸다

# ── 2) 앱 저장소에서 — 지문 대조 후 정식 배포
cd "$LP_APP_DIR"
node test-integration-contract.js
python3 deploy-filestation.py
```

★ **0번을 먼저 확인한다.** 「찾았다」가 안 나오면 그 아래는 전부 헛돈다.
★ `npm run im:embed` 는 자리표시·없는 폴더·`im-flow` 아닌 곳을 **거절하고
  무엇이 잘못됐는지 말한다** — 엉뚱한 곳에 16개를 쏟지 않기 위해서다.

### 2-3. verify:nas 「23통과」는 **라우트 수가 아니다**

본체 문서는 현재 상태를 「verify:nas **23통과**·0실패·0못잼」으로 적었다.
그 숫자는 **점검 항목 수**다. 라우트 수와 헷갈리면 「23개 라우트가 다 있다」로
읽히는데, **지금 라우트는 31개**다 (읽기 6 · 쓰기 25 — 2026-08-24 에 목록 접기와 자료 읽기 진행이 늘었다).

```
읽기 6 · 쓰기 23 = 29
```

★ 「쓰기 23」과 「점검 23」이 **우연히 같은 숫자**라 더 헷갈린다. 라우트 수는
`verify:nas` 출력의 「라우트 표」 줄에서 읽는다.

★ 2026-08-21 에 늘어난 `POST /projects/:id/scan` 이 그 29번째다. **엔진을
배포하기 전까지 NAS 에는 없다** — 그때 `verify:nas` 가 그렇다고 말해야 정상이다.

## 3. ✅ 본체 §7 의 🔴 두 건 — **하나는 끝났고 하나는 절반이다**

### ① `linkpilot-app` 출처 거절 — **끝났다**

본체 문서가 「앱 첨부 가져오기가 막혀 있음」으로 🔴 올린 건이다.
**엔진에서 이미 고쳤다.** 실제로 돌려 확인했다:

```
KNOWN_IDS     : dropbox · box · gdrive · onedrive · linkpilot-app
INTERNAL_IDS  : linkpilot-app
normalizeRef({provider:'linkpilot-app', …})  →  통과
```

- **고르기 창이 있는 저장소**(`PROVIDER_IDS`)와 **아는 출처**(`KNOWN_IDS`)를 갈랐다.
  앱이 넘기는 내부 출처는 고를 창이 없으므로 **단추 목록에는 안 뜬다.** 그게 맞다.
- 검증기가 이제 받는다. 앱은 **바꿀 것이 없다** — 엔진을 배포하면 열린다.

★ 이 사고의 성격은 「문서·화면·검증기 **3중 갈라짐**」이었다. 재발을 막으려고
미리보기의 가짜 서버가 **진짜 검증기 목록을 그대로 심어** 쓴다 — 미리보기만
너그러우면 초록인데 실물은 「첨부 0개」가 된다.

### ② 클라우드폴더 통합(20절) — **§7 하나만 반영, 나머지는 결정 대기**

교차검증은 끝냈다: **일치 7 · 부분 5 · 충돌 4 · 미구현 4.**
**반영한 것은 §7(버전·최신본) 하나**다 — 충돌이 없어서다. 실측:

```
IM_v1.pdf · IM_v2.pdf · IM_Final.pdf  →  한 묶음으로 잡는다
근거 종류가 다르면 「못 가렸다」고 말한다 (여기서 하나를 고르면 그것이 추측이다)
```

나머지는 **§2-1 의 D-72 · D-73 이 정해져야** 어디에 붙일지가 정해진다.
정해지기 전까지 **반쯤 만들지 않는다.**

## 4. ✅ `POST /scan` — **배선이 이미 있을 가능성이 높다**

새 길은 자료를 읽어 값으로 만든다. 본체가 붙일 것을 「한 줄」로 안내했는데,
본체 문서를 읽어 보니 **그 한 줄이 이미 있을 것으로 보인다.**

> 본체 문서 §4 (8/17~18): 「엔진 §6-1/6-2(materialize 파이프라인 연결·**extractInto**) ·
> **oneshot 실측(200·read·삭제)**」

1회성 업로드가 **`read` 를 담아 200 으로 돌아왔다**는 것은, `extractOneshot` 이
실제로 붙어 있다는 뜻이다. 엔진은 `extractFiles` 가 없으면 **`extractOneshot` 을
쓴다** — 둘은 같은 함수를 가리킨다.

**확인은 한 줄이면 된다.** 엔진 배포 뒤 프로젝트 하나로:

```bash
# 프로젝트 번호를 한 번만 정해 두고 이름으로 부른다 (자리표시를 남기지 않는다)
PROJ="LP-DC-2026-001"            # ← 자기 프로젝트 번호로 바꾼다
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$LP_BASE/api/linkpilot/projects/$PROJ/scan"
```

- **200** 이면 배선이 **이미 붙어 있다.**
- **501** 이면 그때 §3 의 한 줄을 더한다. **고장이 아니다.**

★ 501 이 와도 **고장이 아니다.** 「아직 안 붙었습니다」와 「자료는 그대로 있다」를
함께 말하도록 만들어 두었다. 0건을 성공으로 돌려주지 않는 것이 설계다.

## 5. ⚠️ 이 서버에서 **원리상 안 나오는 것** — 미리 알아 둔다

본체 문서가 적은 NAS 사양에서 곧바로 따라오는 결과다. **고장이 아니다.**

### 5-1. 크롬이 없다 → **PDF 3종이 안 나온다**

```
pdf        12_Final/im-a4.pdf            (출력 사양에 PDF 를 넣었을 때만 기대)
desk_pdf   08_Appraisal/desk-review-a4.pdf
corp_pdf   10_Corporate/corp-review-a4.pdf
```

- 최종본은 `12_Final/im-a4.html` 로 나온다 (본체 문서와 같은 말).
- **분모 문제는 §6-2 ①에서 고쳤다.** 브라우저가 없으면 이 셋을 분모에서 빼고,
  목록에는 「이 서버에서는 못 만드는 것」으로 남긴다. 고치기 전에는 사양에
  PDF 를 넣어 두면 **영영 100% 가 안 됐다.**
- **SVG 옆의 JPEG 도 같은 이유로 못 만든다.** 엔진은 그때 **조용히 넘어가지 않고**
  경고와 YELLOW 플래그를 남긴다 — 「있어야 하는데 없다」를 아무도 모르는
  상태를 만들지 않는다.

### 5-2. RAM 1.8GB → **한 번에 너무 많이 읽히지 않는다**

`POST /scan` 은 그 프로젝트의 자료를 읽는다. 자료가 수십 개면 메모리와 시간이
함께 든다. **§6-2 ②에서 상한을 걸었다** — 한 번에 40개 · 200MB 까지 읽고,
남은 것을 이름과 개수로 말한다.

좁혀서 부를 수도 있다:

```json
{ "only": "kept" }     또는     { "only": "linked" }
```

★ **상한 숫자(40개·200MB)가 맞는지는 안 재 봤다** — RAM 1.8GB 에서 어디까지
버티는지 모른다(§8). 지금은 **안전한 쪽으로** 잡아 두었다.

### 5-3. Node 가 PATH 밖이다 → 스크립트가 **절대 경로**를 쓴다

`/usr/local/bin/node`. 크론·스케줄러에서 `node` 로만 부르면 **없다고 나온다.**

### 5-4. OCR 은 키가 있어야 돈다

이미지·스캔본을 옮겨 적으려면 `GEMINI_API_KEY` 가 서버에 있어야 한다.
**없어도 스캔은 돌고 값도 나온다 — 이미지만 빠진다.** 그 사실이 화면에
**파일 단위로** 적힌다. 본체 문서의 「Gemini 새 키는 Interactions API」 이관이
엔진 `llm.js` 에도 반영되어 있어야 이 경로가 산다.

## 6. 🟠 앱이 넘기는 값은 **4키**, 사전은 **111키**

본체 문서 §4 (8/21): 「`fetchAppProject`(내용 facts **4키 매핑**+notes …)」.

- **모자란 것이 아니다.** 사전에 없는 항목을 억지로 끼워 맞추면 문서에
  「출처 있는 값」으로 실린다 — 그래서 앱은 확실한 것만 값으로 넘기고
  나머지는 `notes` 로 넘긴다. **그 판단이 맞다.**
- 나머지 107키는 ① 자료에서 읽어 채우거나(`/scan`) ② 사람이 2단계에서 넣거나
  ③ 계산으로 나온다. **셋 다 아니면 비워 둔다.**
- 앱이 값을 더 넘기고 싶어지면 **사전 키 이름으로** 넘긴다. 이름이 다르면
  거절되고, 거절 사유가 항목별로 돌아간다.

## 6-2. ⭐ 이 대조로 **엔진에 실제로 반영한 것** — 셋

문서만 내고 끝내지 않았다. 결정에 막히지 않는 것부터 고쳤다.

### ① 크롬 없는 서버에서 **PDF 를 「아직」으로 그리지 않는다**

「아직 안 나왔다」와 「여기서는 못 만든다」는 사용자에게 **전혀 다른 말**이다.
앞엣것은 기다리게 하고, 뒤엣것은 다른 길(최종본 HTML 인쇄)을 찾게 한다.

- `OUTPUTS` 표에 `needsBrowser` 를 적었다 (PDF 세 종).
- 서버가 브라우저를 못 찾으면 그 셋을 **분모에서 뺀다.** 안 그러면
  **어떤 딜도 100% 가 되지 않는다** — 다 끝났는데 덜 된 것처럼 보인다.
- **목록에서는 지우지 않는다.** 「이 서버에서는 못 만드는 것」 무리로 따로 내고,
  이유와 **대신 볼 것**을 적는다.
- `GET /reports` 가 `hasBrowser` 를 함께 준다. 화면이 짐작하지 않는다.

★ **모르면 빼지 않는다.** 브라우저를 못 찾겠으면 `null` 이고, 그때는 아무것도
빼지 않는다 — 되는 서버에서 PDF 가 목록에서 사라지는 쪽이 더 나쁘다.

### ② 스캔이 **한 번에 너무 많이 읽지 않는다** (RAM 1.8GB)

한 번에 **40개 · 200MB** 까지 읽는다. 넘으면 거기서 멈춘다.

★★ **조용히 자르지 않는다.** 자른 것을 이름으로 돌려주고, 몇 개 남았는지
(`remaining`) 함께 말한다. 화면은 「양이 많아 N개를 아직 안 읽었습니다 —
다시 누르면 이어서 읽습니다」로 그리고, **남은 것이 있으면 2단계로 넘기지
않는다** — 반만 읽은 값으로 넘어가면 왜 어떤 칸만 비었는지 알 수가 없다.

### ③ **D-번호 갈림을 등록부에 올렸다** (D-77)

정하기 전까지 **번호만 적힌 지시는 반영하지 않는다.** 내용을 확인하고 어느 쪽
D 인지 밝힌 뒤에 손댄다.
