# 업로드 본문 한도를 올리는 법 — 엔진 서버와 리버스 프록시

〈2026-08-22 작성 · **같은 날 정정** — 아래 「정정」 참고〉

---

## 실측으로 밝혀진 것 〈2026-08-22 · 배포 워크플로 probe〉

**이 문서가 처음에 짐작한 「express 기본 100KB」는 틀렸다.** NAS 는 express 를
쓰지 않는다. 실제로 요청을 보내 재 보니 이렇다 (8181 직행 · 없는 프로젝트로
보내 아무것도 바꾸지 않았다):

| 본문 | 결과 |
|---|---|
| 1MB · 8MB · 24MB · 48MB | HTTP 401 — **끝까지 갔다** |
| 64MB | 여기가 벽이다 |

```js
// /volume1/docker/linkpilot/im-engine-server.cjs
const MAX_BODY = 64 * 1024 * 1024;
req.on('data', (c) => { size += c.length; if (size > MAX_BODY) { req.destroy(); } else chunks.push(c); });
```

그래서 **아래 ①-(가) 의 express 절차는 이 NAS 에 해당하지 않는다.** 고칠 자리는
`MAX_BODY` 한 줄이다. 다만 **얼마로 할지는 아직 정하지 않았다** — 엔진은
100MB 를 약속하는데 서버는 64MB 다. `docs/미결정-사항.md` D-81 에 올려 두었다.

**그리고 8.7MB 가 멈춘 원인은 이것이 아니다.** 8MB 는 통과했다. 원인은
아직 잡히지 않았고, 휴대폰이 실제로 지나는 **Funnel(443)** 쪽을 재야 한다.

---

## 정정 — 고칠 파일이 다르다

처음 이 문서는 「앱 본체(`linkpilot-platform`)의 Node API」를 고치라고 적었다.
**그런 것은 없다.**

NAS 구성을 다시 확인한 결과는 이렇다 (`docs/작업지시서-플랫폼-연동.md` §3):

| | 실제 |
|---|---|
| 앱 | `linkpilot-platform.deploy.html` — **미리 컴파일된 단일 HTML 파일**. DSM 웹서버(80)가 그냥 내려준다. Node 가 아니다 |
| 로그인 | `login.php` — PHP |
| **Node 프로세스** | **`im-engine-server.cjs` 하나뿐이다** (8181) |
| 길 | Tailscale Funnel 443 → 80(앱) · **`/api/linkpilot/*` → 8181(엔진)** |

업로드는 `/api/linkpilot/projects/…/oneshot` 으로 간다. 즉 **앱을 거치지 않고
엔진 서버로 곧장** 간다. 그러니 본문 한도가 걸려 있는 곳도 **엔진 서버 파일**이다.

**틀린 문서대로 찾으면 없는 파일을 한참 뒤진다.** 그래서 지운 것이 아니라
정정으로 남긴다.

---

## 왜 올려야 하나

엔진은 파일 하나 30MB · 한 번에 100MB 까지 받도록 되어 있다. 그런데
**엔진의 그 검사에 닿기도 전에 끊기는 자리가 하나 더 있다.**

```
휴대폰 ──▶ Funnel(443) ──▶ 리버스 프록시 ──▶ im-engine-server.cjs (8181)
                              ▲                    ▲
                              │                    └── ② 본문 파서의 한도
                              │                        (express 기본값 100KB)
                              └── ① 프록시의 본문 한도
                                  (nginx 기본값 1MB)
```

**여기서 끊기면 오류가 전혀 다른 얼굴로 나온다.** 화면에는 「파일 하나 30MB 까지
올릴 수 있습니다」라고 적혀 있는데 8MB 짜리를 올리면 그냥 멈추거나
「전송이 끊겼습니다」가 뜬다. **화면이 말하는 한도와 실제로 걸리는 한도가 달라서**
「30MB 라더니 왜 안 되나」로 한참 헤매게 된다.

---

## 얼마로 잡나

파일은 **base64** 라는 방식으로 글자로 바꿔 실려 온다 — 원본보다 약 **33% 크다.**

| | 파일 크기 | 실려 오는 본문 |
|---|---|---|
| 파일 하나 | 30 MB | 약 **40 MB** |
| 한 번에 | 100 MB | 약 **133 MB** |

그래서 본문 한도는 **최소 141MB** 로 잡는다 (여유 8MB 포함).
이 값은 엔진이 계산해서 내준다 — **손으로 적지 않는다.**

```js
const { MIN_BODY_BYTES } = require('/volume1/docker/linkpilot/im-agent/ui/api-router.cjs');
```

## ① 엔진 서버 — `im-engine-server.cjs`

**파일 위치** `/volume1/docker/linkpilot/im-engine-server.cjs`
(이 저장소에는 없다. NAS 에만 있다)

### 1) 접속해서 지금 무엇으로 파싱하는지 본다

```bash
ssh <계정>@<NAS주소>
cd /volume1/docker/linkpilot
grep -n "express.json\|bodyParser\|JSON.parse" im-engine-server.cjs
```

나오는 모양에 따라 고치는 자리가 다르다.

**(가) `express.json(` 이 있으면** — 그 줄에 `limit` 만 더한다.

```js
const { MIN_BODY_BYTES } = require('./im-agent/ui/api-router.cjs');

app.use(express.json({ limit: MIN_BODY_BYTES }));   // 약 141MB
```

> **여기서 대개 막힌다** — `express.json()` 이 이미 걸려 있는데 새로 하나 더
> 거는 것. 앞에 걸린 것이 본문을 **먼저** 먹으므로 여전히 100KB 에서 끊긴다.
> **새로 걸지 말고 있는 줄을 고친다.**

**(나) `express` 가 안 보이고 `req.on('data', …)` 로 직접 모으면** — 그 자리에
길이 검사가 있을 것이다. 그 숫자를 `MIN_BODY_BYTES` 로 바꾼다.

### 2) 재시작

`.env` 와 코드는 **띄울 때 한 번만 읽는다.** 고치기만 하면 안 바뀐다.

```bash
cd /volume1/docker/linkpilot
./stop-engine.sh && ./start-engine.sh
tail -20 engine.log
```

### 3) 살아났는지 확인

```bash
curl -s http://127.0.0.1:8181/healthz
```

`{"ok":true,…}` 가 나와야 한다.

> **되돌리는 법을 먼저 만들어 둔다.** 고치기 전에
> `cp im-engine-server.cjs im-engine-server.cjs.bak` 을 한 번 친다.
> 이 프로세스가 안 뜨면 **자료 업로드·보고서 생성이 전부 멈춘다.**

## ② 앞단 리버스 프록시

Funnel 뒤에 Synology 역방향 프록시나 nginx 가 있으면 **거기에도 한도가 있다.**
nginx 기본값은 `client_max_body_size 1m` 이다.

```nginx
client_max_body_size 141m;
```

DSM 에서는 **제어판 → 응용 프로그램 포털 → 역방향 프록시** 로 들어가
해당 규칙을 고른 뒤 **[편집]** 을 누른다. 그리고 **사용자 지정 헤더** 탭이 아니라
**고급 설정** 탭이다.

> **여기서 대개 막힌다** — 「사용자 지정 헤더」 탭만 보고 「그런 설정이 없다」고
> 넘어가는 것. 본문 크기는 **고급 설정** 쪽에 있다.

## 넣고 나서 — 어디서 끊겼는지 가르는 법

「자료 업로드」 탭에서 **8MB 짜리 파일 하나**를 올려 본다.
「올렸습니다」가 뜨면 된 것이다. 안 되면 **나오는 말로 자리를 가른다.**

| 나오는 말 | 어디서 끊겼나 | 할 일 |
|---|---|---|
| `413` · `PayloadTooLargeError` | **엔진의 본문 파서** — 아직 옛 한도다 | ① 을 다시 본다 (두 번 걸리지 않았는지) |
| 「전송이 끊겼습니다」 · 응답 없이 멈춤 | **앞단 프록시**일 가능성이 크다 | ② |
| 「파일이 너무 큽니다 — N MB (한도 30.0 MB)」 | **엔진의 정상 동작이다** | 파일을 나눠 올린다 |
| 「로그인이 필요합니다」가 뜨는데 목록은 보였다 | 큰 본문이 앞단에서 잘려 나간 것 | ② |

마지막 줄이 특히 헷갈린다. **목록은 잘 보였는데 올릴 때만 로그인 화면이 뜨면
그것은 로그아웃된 것이 아니다** — 본문이 통째로 잘린 것이다.

## 함께 봐 둘 것 — 메모리

운영 NAS 는 **RAM 1.8GB** 다. 133MB 본문을 파싱하면 문자열과 디코드 버퍼로
순간 **300MB 안팎**을 쓴다. 한 사람이 올릴 때는 견디지만,
**여럿이 동시에 100MB 를 올리는 상황을 견디는 값은 아니다.**

그때는 엔진 한도를 낮추는 것이 아니라 **동시 업로드 수를 제한한다** —
한도를 낮추면 큰 파일을 아예 못 올리게 되어 원래 요청이 무의미해진다.
